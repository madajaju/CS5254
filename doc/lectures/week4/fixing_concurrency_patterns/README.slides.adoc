== Worked Example: Problem Setup

* **Podcast Domain**:
  * Locking: `ReentrantLock` around `episode.publish()`
  * Immutability: New `Episode` object instead of modification
  * Message Passing: `CleanupComplete` message sent to `Orchestrator`

== Naive Implementation

* Assumes:
  * Operation happens once in order
  * Current state is always accurate
* Execution flow:
  * actor performs operation
  * system reads current state
  * system applies transition
  * system emits side effect

== Failure Scenario

* Issues under overlapping execution, delayed delivery
* Observes stale state, executes twice, stuck workflow
* Mismatch between design assumption and execution model

== Improved Design Direction

* Name invariant, make transitions observable
* Add controls: version checks, idempotency keys
* Solutions: state-machine guards, coordination, retries

== Why Improved Design Is Safer

* Transforms workflow hopes into provable correctness
* Rejects invalid interleavings with evidence

== Failure Modes and Anti-Patterns

* **Symptom**: Passes happy-path test
  * *Why*: Avoids timing, ordering, or pressure conditions
  * *Detection*: Add repeated runs, concurrent actors
  * *Correction*: Add failure-focused tests targeting invariant

* **Symptom**: Names tools, not design properties
  * *Why*: Focus on mechanisms over invariants
  * *Detection*: Ask which invariant is protected
  * *Correction*: State invariant, then select mechanism

* **Symptom**: Vague evidence for claims
  * *Why*: Logs lack detailed info
  * *Detection*: Reviewer can't reconstruct failures
  * *Correction*: Capture structured evidence linked to claims

* **Symptom**: Fix changes behavior, unmeasured against baseline
  * *Why*: No repeatable scenario preserved
  * *Detection*: No before/after run comparison
  * *Correction*: Maintain failing test, rerun after redesign

== Trade-Off Analysis

[cols="1,1,1,1", options="header"]
|===
| Approach | Strengths | Weaknesses | When to Use
| Simple baseline | Easy to explain | Hides timing assumptions | First implementation
| Guarded transition | Protects core invariant | Needs careful modeling | Status changes
| Explicit coordination | Visible dependencies | May cause waiting | Multi-object workflows
| Idempotent design | Handles duplicates | Requires deduplication | Queues, retries
| Observability-first | Strong evidence | Adds instrumentation | Assignments needing failure proof
|===

== Practical Application

* Identify relevant invariant for concurrency patterns
* Write sequential scenario expected to succeed
* Write pressure scenario that could expose failures
* Add operation IDs to logs before running pressure scenarios
* Capture before/after evidence for fixes
* Update Integrity Packet with assumptions and validation
