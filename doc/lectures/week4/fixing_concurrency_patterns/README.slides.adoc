= Fixing Concurrency Patterns

== Lecture Goals

* Diagnose why a sequential demo can appear correct
* Identify the invariant under concurrency pressure
* Reproduce failure with overlapping execution
* Choose a correction that protects the invariant
* Produce evidence suitable for the Integrity Packet
* Connect the fix to A1 deliverables

== Hidden Assumption

* A method name can make a transition sound atomic
* Sequential tests often avoid overlap
* Shared state can be read twice before either write commits
* Logs can hide the losing worker
* Correctness depends on the invariant, not the demo

== Core Patterns

* Locks protect a critical section
* Immutability removes shared mutation
* Message passing avoids shared ownership
* Atomicity joins check and update
* Invariants define what must remain true
* Evidence proves the design survived pressure

== Locks

* A lock allows one thread into a protected section
* The protected section should be small
* The invariant must be named before choosing the lock
* Logs should show entry, decision, and rejection
* Trade-off: less parallelism around the protected entity

== Immutable Design

* Do not modify an object after construction
* Create a new value for each state change
* Thread safety improves because old values remain stable
* Trade-off: more object creation and version management
* Still needs coordination when publishing the new value

== System Invariant

* An invariant is a condition that must remain true
* For the episode example: one worker owns a transition
* The invariant matters more than the mechanism name
* A failing test should target the invariant directly
* A passing fix should show rejected stale work

== Pressure Test Sketch

[source,text]
----
repeat 1000 times:
  reset episode-42 to DRAFT
  start worker A with delay after read
  start worker B with delay after read
  wait for both workers
  assert exactly one claim was accepted
  record workerId, episodeId, previousState, newState, outcome
----

== Design Options

[.stretch]
[cols="1,1,1,1", options="header", width="100%"]
|===
|Approach |Strength |Weakness |Use When

|Lock |Simple exclusion |Can bottleneck |One object must be protected
|Immutable value |Stable snapshots |Needs publication control |Reads dominate writes
|Actor queue |Single owner |Adds queue latency |Workflow ownership is clear
|Compare and set |Direct atomic guard |Requires expected version |State transition is compact
|===

== Baseline and Fix

[.columns]
[.column]
* Baseline splits check and write
* Two workers can pass the check
* Duplicate work can be hidden

[.column]
* Corrected claim is atomic
* Losing worker is rejected
* Logs show both decisions

== Failure Modes

* Happy-path tests avoid the pressure condition
* Tool-first explanations skip the protected property
* Logs lack entity IDs or transition outcomes
* Fixes are not compared to the failing baseline
* Trade-offs are hidden instead of defended

== Integrity Packet

* State the invariant
* Describe the hidden assumption
* Preserve the failing scenario
* Show before and after evidence
* Explain the chosen mechanism
* Name the remaining risk
