== Naive Implementation

A naive design assumes:
- Operation happens once, in order
- Method name sounds correct
- Sequential test passes

== Failure Scenario

*Under pressure:*
- Overlapping execution, stale state
- Same operation can observe stale state or execute twice

== Improved Design Direction

*Safer Design:*
- Name the invariant
- Make the transition observable
- Add correctness controls: version checks, retries

== Why Improved Design Is Safer

*From hoping to proving:*
- Reject invalid interleavings
- Contain or recover failures using evidence

== Failure Modes

*Symptom: Passes happy-path test*
- Detect: Add concurrent tests, logs
- Correct: Add failure-focused test

*Symptom: Names tools, not properties*
- Detect: Ask which invariant is protected
- Correct: State the invariant first

== Failure Modes

*Symptom: Vague evidence*
- Detect: Reviewer cannot reconstruct failure
- Correct: Capture structured evidence

*Symptom: Fix isn't compared to baseline*
- Detect: No before/after runs
- Correct: Preserve failing tests

== Trade-Off Analysis

[cols="1,1,1,1", options="header"]
|===
| Approach | Strengths | Weaknesses | When to Use
| Simple baseline | Easy to explain and implement | Hides timing assumptions | First implementation
| Guarded state | Protects core invariant | Needs careful modeling | Status changes
| Explicit coordination | Makes dependencies visible | Can introduce deadlock | Multi-object workflows
| Idempotent design | Handles duplicates | Requires keys or side-effect control | Async workers
| Observability design | Produces strong evidence | Adds instrumentation | Design defense
|===
