= Tradeoffs
:revealjs_theme: black
:source-highlighter: highlight.js

== Learning Objectives

* Analyze design pressure in a stateful concurrent system.
* Diagnose hidden assumptions behind a passing demo.
* Evaluate failure evidence from logs, traces, interleavings, or tests.
* Design a correction that preserves the invariant.
* Defend the decision in the Integrity Packet for A1.

== Opening Pressure

* A project appears correct in a simple demonstration.
* Concurrency, ambiguity, or operational pressure changes the execution model.
* The hidden assumption is often about Performance vs. Correctness.
* The engineer must identify what must remain true.
* The design is trustworthy only when evidence supports the claim.

== Core Question

* Not whether the code can run once.
* Not whether the happy path looks plausible.
* Ask which invariant must survive pressure.
* Ask what evidence proves the invariant survived.
* Ask what cost the protection introduces.

== System Invariant

* An invariant is a condition that must remain true across valid executions.
* For the episode workflow, only one worker may own a transition at a time.
* The invariant must be named before choosing a mechanism.
* The test must apply pressure to the invariant.
* The logs must show the transition and the rejected attempt.

== Failure Evidence

* Repeat the pressure test many times.
* Add delay between read and write.
* Log worker ID, episode ID, previous state, new state, and timestamp.
* Preserve the failing run as the baseline.
* Compare the same run after the fix.

== Design Response

* Name the protected property before naming the tool.
* Choose the simplest mechanism that protects the transition.
* Make rejection explicit, not silent.
* Log enough detail for a reviewer to reconstruct the run.
* State the tradeoff introduced by the control.

== Interview Questions

* What invariant matters most in your design?
* What hidden assumption made the baseline appear correct?
* How did you force the failure repeatedly?
* What log line proves the rejected transition?
* What tradeoff did your correction introduce?
* What remaining risk belongs in the Integrity Packet?

== Summary

* Tradeoffs are design pressure, not vocabulary.
* A passing demo can hide a false execution model.
* Correctness depends on a named invariant.
* Evidence must show what happened under pressure.
* The final design must protect the property and disclose the cost.
