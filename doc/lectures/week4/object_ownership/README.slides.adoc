== Opening Narrative

* A project seems correct during a simple demo.
* Concurrency exposes hidden assumptions.
* Analysis and defense are required before trusting the result.

== Thread Confinement

* **Definition**: Restricting object access to a single thread.
* **Importance**: Must be explicit for system trust.
* **Mechanism**: State, timing, worker behavior, retries.
* **Failure Mode**: Ignored confinement leads to duplicates, staleness.
* **Design Implication**: Log transitions, validate with tests.

== System Invariant

* **Definition**: Condition true across all valid executions.
* **Importance**: Critical for system trust under pressure.
* **Mechanism**: State, timing, behavior.
* **Failure Mode**: Leads to misleading evidence and blocked progress.
* **Design Implication**: Expose invariant, log transitions.

== Failure Mode

* **Definition**: Repeatable way to violate an invariant.
* **Importance**: Critical for system trust under pressure.
* **Mechanism**: State, timing, behavior.
* **Failure Mode**: Duplicate work, staleness, blocked progress.
* **Design Implication**: Log transitions, validate behavior.

== Design Trade-Off

* **Definition**: Choice between competing qualities.
* **Importance**: Must be explicit for system trust.
* **Mechanism**: State, timing, behavior.
* **Failure Mode**: Misleading evidence.
* **Design Implication**: Log transitions, validate behavior.

== Worked Example: Podcast Domain

* **Confinement**: `Cleaner` thread owns `AudioAsset` during cleaning.
* **Hand-off**: Cleared reference after `Publisher` takes over.
* **Queue-Based Ownership**: Ownership transferred to the consumer.

== Naive Implementation Model

* Assumes single operation in order with current state:
  * Actor performs operation
  * System reads current state
  * System applies transition
  * System emits side effect

== Failure Scenario

* Issues arise under delays, retries, or overlapping executions.
* Same operation may:
  * Observe stale state
  * Execute multiple times
* Assumption mismatch with execution model.

== Improved Design Direction

* Name the invariant and make transitions observable.
* Add:
  * Version checks
  * Idempotency keys
  * State-machine guards
  * Coordination mechanisms

== Why the Design Is Safer

* Shifts from hope to proof of invalid interleavings being contained.
* Evidence-based validation enhances trust.

== Anti-Patterns: System Weaknesses

* **Symptom**: Passes single happy-path test.
  * **Detection**: Use concurrent actors or stress tests.
  * **Correction**: Add failure-focused tests.

== Failure Modes Continued

* **Symptom**: Focuses on tools rather than design properties.
  * **Detection**: Check for stated invariant protection.
  * **Correction**: Write invariant before mechanism.

* **Symptom**: Vague evidence does not support claims.
  * **Detection**: Lack of structured logs.
  * **Correction**: Capture evidence linked to claims.

== Trade-Off Analysis Table

[cols="1,1,1,1", options="header"]
|===
| Approach | Strengths | Weaknesses | When to Use
| Simple baseline | Easy to implement | Hides timing assumptions | Initial implementation
| Guarded transition | Protects core invariant | Requires careful modeling | Status changes
| Explicit coordination | Makes dependencies visible | Can cause bottlenecks | Multi-object workflows
| Idempotent design | Handles duplicates | Requires management keys | Queues, retries
| Observability-first | Strong evidence for review | Adds instrumentation | Failure proof assignments
|===
