= Object Ownership & Thread Confinement

== Why this lecture matters

* A sequential demo can make unsafe ownership look correct.
* Thread confinement asks which thread may touch which object.
* The central invariant must be named before the fix is chosen.
* Evidence must show what happened under pressure.
* A1 asks you to defend the design, not just show that it runs.

== Learning Objectives

* Analyze ownership and confinement pressure in a stateful concurrent system.
* Diagnose hidden assumptions in the baseline design.
* Evaluate logs, traces, interleavings, and repeatable test output.
* Design a control that preserves the invariant.
* Defend the choice in the Integrity Packet.

== What Evidence Must Show

* Which worker or thread acted.
* Which entity was touched.
* What previous state was observed.
* What new state was attempted.
* Whether the operation won or lost.
* Whether the result repeats under the same test.

== Design Response Options

[.stretch]
[cols="1,1,1,1", options="header", width="100%"]
|===
|Approach |Protects |Cost |Use When

|Atomic compare-and-set
|Single transition winner
|More explicit update logic
|One record owns the state

|Synchronized transition
|One thread enters at a time
|Possible contention
|Object boundary is clear

|Single-owner queue
|One consumer owns work
|Throughput bottleneck risk
|Work can be serialized

|Idempotency key
|Duplicate side effects
|Key storage and lookup
|Retries are expected
|===

== Trade-Off Comparison

[.stretch]
[cols="1,1,1,1", options="header", width="100%"]
|===
|Design |Strength |Weakness |Best Fit

|Simple baseline
|Easy to explain
|Hides timing assumptions
|Initial comparison

|Guarded transition
|Protects invariant directly
|Requires state modeling
|Workflow status changes

|Explicit coordination
|Makes order visible
|Can block progress
|Multi-object operations

|Observability-first
|Supports review evidence
|Adds instrumentation work
|A1 design defense
|===

== Failure Anti-Patterns

* Passing one demo and treating it as proof.
* Naming a tool before naming the invariant.
* Logging messages that omit entity IDs.
* Losing the failing test after the redesign.
* Explaining the fix without stating the trade-off.
* Claiming safety without repeatable pressure evidence.

== Interview Checks

* What object is confined, and to which thread or owner?
* What invariant would be violated by overlapping execution?
* How would you force the bad interleaving?
* What log line proves the loser was rejected?
* What trade-off does your correction introduce?
* What remains risky after the fix?

== Summary

* Object ownership is a correctness boundary.
* Thread confinement works only when access is actually restricted.
* The invariant is the center of the argument.
* Pressure tests reveal hidden assumptions.
* Evidence turns the design claim into a defensible A1 artifact.
