== Naive Implementation

* Operation occurs once, in order
* Method name seems correct, passes sequential tests

== Failure Scenario

* Concurrently, can observe stale state
* Failure: mismatch between design assumption and execution model

== Improved Design Direction

* Name invariant, observe transitions, add controls
* Use version checks, idempotency keys, state machine guards

== Why Improved Design Is Safer

* Proves invalid interleavings are rejected or managed

== Failure Modes & Anti-Patterns

* Symptom: System passes single demo
  * Detection: Add concurrent actors, structured logs
  * Correction: Maintain happy-path test, add failure-focused tests

* Symptom: Names tool, not design property
  * Detection: Ask which invariant is protected
  * Correction: Write invariant first, then select mechanism

* Symptom: Evidence is too vague
  * Detection: Reviewer cannot reconstruct failure
  * Correction: Capture structured evidence linking to claims

* Symptom: Fix not compared to baseline
  * Detection: No repeatable failing scenario
  * Correction: Preserve failing test and rerun post-redesign

== Trade-Off Analysis

[cols="1,1,1,1", options="header"]
|===
| Approach | Strengths | Weaknesses | When to Use
| Simple baseline | Easy to implement | Hides timing assumptions | First implementation
| Guarded transition | Protects core invariant | Requires careful modeling | Reservations, publishing
| Explicit coordination | Makes dependencies visible | Can introduce deadlock | Multi-object workflows
| Idempotent design | Handles duplicates | Requires deduplication | Queues, async workers
| Observability-first | Strong evidence | Adds instrumentation | Assignments requiring proof
|===
