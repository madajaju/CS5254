= Validating Fixes

== Learning Objectives

* Analyze the pressure created by validating fixes in a stateful concurrent system.
* Diagnose hidden assumptions that make a baseline appear correct.
* Evaluate failure evidence using logs, traces, interleavings, or repeated tests.
* Design a correction that preserves the relevant invariant.
* Defend the chosen approach in the Integrity Packet.
* Connect the validation story to A1 deliverables.

== Central Question

* A project passes a simple demonstration.
* Concurrency, ambiguity, or operational pressure is introduced.
* A hidden assumption about fix verification is exposed.
* The engineer must decide what evidence proves the fix.
* The goal is not one clean run.
* The goal is reliable preservation of the invariant.

== Fix Verification

* Re-run the exact test that previously failed.
* Confirm the failure no longer appears reliably.
* Keep the original failing scenario as a regression test.
* Use repeated runs rather than one lucky execution.
* Compare before and after evidence.
* Explain which invariant is now protected.

== Hidden Assumption

* The method name sounds atomic.
* The code actually performs separate steps.
* A sequential test hides the timing gap.
* Two workers can observe the same old state.
* The final state may look normal while duplicate work happened.
* Validation must expose the gap.

== Evidence Requirements

* Include operation ID and entity ID.
* Record worker or thread ID.
* Capture previous state and new state.
* Preserve timestamps or ordering markers.
* Repeat the pressure scenario.
* Compare before and after output.

== Trade-Off Analysis

[.stretch]
[cols="1,1,1,1", options="header", width="100%"]
|===
|Approach |Strengths |Weaknesses |When to Use
|Simple baseline |Easy to explain |Hides timing assumptions |Initial comparison point
|Guarded transition |Protects invariant directly |Requires state modeling |Status changes and reservations
|Explicit coordination |Makes dependencies visible |Can create bottlenecks |Multi-object workflows
|Idempotent design |Handles duplicates |Needs keys and deduplication |Queues and retries
|===

== Mechanism Choices

[.stretch]
[cols="1,1,1,1", options="header", width="100%"]
|===
|Mechanism |Protects |Evidence |Trade-Off
|Compare-and-set |Single state owner |Rejected stale update |Database-specific logic
|Synchronized method |Critical section |One entry at a time |Lower parallelism
|Single-owner queue |Ordered handling |Serialized event log |Queue latency
|Idempotency key |Duplicate side effects |Key reuse record |More storage
|===

== A1 Application

* Choose one object or workflow in your project.
* State the invariant that must survive pressure.
* Create one sequential success scenario.
* Create one pressure scenario that could fail.
* Add structured evidence before fixing.
* Record the validation story in the Integrity Packet.

== Interview Questions

* What invariant is most relevant?
* What hidden assumption made the baseline appear correct?
* How would you force the failure repeatedly?
* What evidence proves the failure happened?
* Which mechanism would you choose first?
* What trade-off does your mechanism introduce?
