= AI-Generated Designs: Common Flaws

== Learning Objectives

* Diagnose hidden assumptions in AI-generated concurrent designs
* Identify invariants before choosing mechanisms
* Force failures with repeatable pressure scenarios
* Evaluate evidence from logs, traces, and interleavings
* Defend a correction in the Integrity Packet

== Core Claim

* AI output can be a useful draft
* AI output is not correctness evidence
* Concurrent pressure exposes assumptions that sequential examples hide
* A design is mature only when its invariant survives bad timing
* A1 rewards evidence-backed reasoning, not tool confidence

== Common Flaws

* Thread-safety hallucinations
* Missing edge cases
* Complexity overload
* Assumed atomicity
* Unsupported claims about correctness
* Vague evidence that cannot be replayed

== Failure Evidence

* The failure is not syntax
* The failure is a mismatch with the execution model
* Required log fields are worker ID, episode ID, previous state, new state, and time
* Repeat the test until the interleaving is visible
* Preserve the failing run for before and after comparison

== Design Response

* Name the invariant first
* Protect the state transition directly
* Reject stale or competing claims
* Log accepted and rejected transitions
* Keep the simplest mechanism that produces reviewable evidence

== Trade-Off Analysis

[.stretch]
[cols="1,1,1,1", options="header", width="100%"]
|===
|Approach |Strengths |Weaknesses |When to Use

|Simple baseline
|Easy to explain
|Hides timing assumptions
|Initial comparison point

|Guarded transition
|Protects invariant directly
|Requires state modeling
|Status and workflow changes

|Explicit coordination
|Makes ordering visible
|Can create bottlenecks
|Multi-object workflows

|Idempotent design
|Handles duplicate attempts
|Needs keys and deduplication
|Retries and external calls

|Observability first
|Supports review
|Adds instrumentation work
|Integrity Packet evidence
|===

== Practical Checklist

* Identify the invariant or progress property
* Write one sequential success scenario
* Write one pressure scenario
* Add operation IDs and entity IDs before testing
* Capture before and after evidence
* Record the assumption, validation, and remaining risk

== Assignment Integration

* Connect the flaw to your A1 project domain
* Show the object, workflow, event, or recovery mechanism
* Include runnable evidence, not just explanation
* Compare the baseline with the corrected design
* Defend the trade-off in the Integrity Packet

== Interview Questions

* What invariant matters most here?
* What hidden assumption made the baseline appear correct?
* How would you force the failure repeatably?
* What log line proves the losing worker was rejected?
* What trade-off does your chosen mechanism introduce?

== Summary

* AI-generated designs are hypotheses
* Concurrency turns hidden assumptions into failures
* Correctness depends on protected invariants
* Evidence must be replayable and reviewable
* The Integrity Packet connects the claim, test, decision, and risk
