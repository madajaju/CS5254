== Improved Design Direction

* Define the invariant clearly
* Make transitions observable
* Add correctness checks (e.g., version checks)

== Why Improved Design Is Safer

* Moves from assumptions to proof
* Prevents invalid interleavings
* Protects workflow integrity with evidence

== Failure Modes & Anti-Patterns

* Symptom: Happy-path tests pass
  * Cause: Avoids pressure conditions
  * Detect: Use diverse tests
  * Correct: Add failure-focused tests

* Symptom: Tool names without properties
  * Cause: Failing to state invariants
  * Detect: Inquire about invariant protection
  * Correct: State invariant first

* Symptom: Vague evidence for claims
  * Cause: Lack of detailed logs
  * Detect: Poor reconstruction of failures
  * Correct: Capture structured evidence

* Symptom: Fixes change behavior in isolation
  * Cause: History of repeatable failures lost
  * Detect: No baseline comparisons
  * Correct: Preserve failing tests

== Trade-Off Analysis

[cols="1,1,1,1", options="header"]
|===
| Approach | Strengths | Weaknesses | When to Use
| Simple baseline | Easy to explain | Hides timing assumptions | Initial comparison point
| Guarded transition | Protects core invariant | Requires careful modeling | Status changes or workflows
| Explicit coordination | Makes dependencies visible | May introduce wait issues | Complex workflows needing order
| Idempotent design | Handles duplicates | Needs deduplication | Queues, retries, async scenarios
| Observability-first | Strong evidence generation | Adds instrumentation work | Requires design defense
|===
