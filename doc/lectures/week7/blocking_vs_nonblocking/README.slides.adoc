== Core Concept: Blocking

* Definition: Thread stops and waits
* Importance: Must be explicit before trust
* Mechanism: Through state, timing, behavior
* Failure Mode: Leads to duplicates, stale state, or misleading evidence
* Design Implication: Expose invariant, log transition, validate behavior

== Core Concept: Non-Blocking

* Definition: Thread continues while waiting
* Importance: Must be explicit before trust
* Mechanism: Through state, timing, behavior
* Failure Mode: Same as Blocking
* Design Implication: Expose invariant, log transition, validate behavior

== Core Concept: Thread Starvation

* Definition: All threads blocked waiting
* Importance: Must be explicit before trust
* Mechanism: Through state, timing, behavior
* Failure Mode: Same as Blocking
* Design Implication: Expose invariant, log transition, validate behavior

== Core Concept: Callbacks/Promises

* Definition: Handles completion notifications
* Importance: Must be explicit before trust
* Mechanism: Through state, timing, behavior
* Failure Mode: Same as Blocking
* Design Implication: Expose invariant, log transition, validate behavior

== Core Concept: Coordination Boundary

* Definition: Point of agreement on ordering
* Importance: Must be explicit before trust
* Mechanism: Through state, timing, behavior
* Failure Mode: Same as Blocking
* Design Implication: Expose invariant, log transition, validate behavior

== Worked Example: Problem Setup

* Podcast Domain: 
  * Blocking: `Orchestrator` sleeps until `cleaner.clean()`
  * Non-Blocking: `Orchestrator` requests `Cleaner` while fetching new episodes
* I/O Wait: Blocking reads vs. asynchronous design

== Worked Example: Naive Implementation

* Naive design assumptions:
  * Operation happens once and in order
  * Method name sounds correct
  * Sequential test passes

```text
actor performs operation
system reads current state
system applies transition
system emits side effect
```

== Worked Example: Failure Scenario

* Overlapping execution causes:
  * Stale state 
  * Duplicate execution 
  * Workflow gets stuck 
* It's a design assumption mismatch, not just syntax.

== Worked Example: Improved Design Direction

* Name the invariant
* Make transitions observable
* Add controls like:
  * Version checks
  * Idempotency keys
  * State-machine guards

== Why Improved Design Is Safer

* Shift from assuming order to proving correctness
* Reject or recover invalid interleavings with evidence

== Failure Modes and Anti-Patterns

* Symptom: Passes happy-path test.
  * Why: Test avoids timing or pressure conditions.
  * Correct: Add failure-focused tests.
* Symptom: Names a tool, not a design property.
  * Why: Focus on mechanisms before invariants.
  * Correct: Write the invariant first.
* Symptom: Vague evidence.
  * Why: Logs lack critical IDs or information.
  * Correct: Capture structured evidence.

== Trade-Off Analysis

[cols="1,1,1,1", options="header"]
|===
| Approach | Strengths | Weaknesses | When to Use
| Simple baseline | Easy to explain | Hides timing assumptions | First implementation
| Guarded transition | Protects invariant | Requires careful modeling | Status changes
| Explicit coordination | Visible dependencies | May cause waiting | Multi-object workflows
| Idempotent design | Handles duplicates | Needs side-effect control | Queues and retries
| Observability-first | Produces strong evidence | Adds instrumentation | Assignments requiring proof
|===
