= Blocking vs. Non-Blocking Coordination

== Lecture Goals
* Analyze blocking vs. non-blocking coordination as a design pressure.
* Identify hidden assumptions that make a concurrent workflow look correct.
* Use logs, traces, and repeatable tests as evidence.
* Choose a correction that preserves the invariant.
* Connect the conclusion to Integrity Packet and A2 work.

== Blocking
* A thread waits and does no other work.
* Useful when waiting is explicit and bounded.
* Risky when waiting hides progress loss.
* The key question is whether the wait preserves the invariant.

== Non-Blocking
* A thread starts work and continues with other tasks.
* Completion is reported later by callback, promise, or event.
* Useful when throughput and responsiveness matter.
* The key question is whether completion is observable and ordered correctly.

== Coordination Boundary
* The boundary is where objects must agree on ordering.
* The boundary is where ownership must be clear.
* The boundary is where progress can be lost.
* The boundary is where evidence should be logged.

== Thread Starvation
* All available threads can become blocked.
* New requests stop making progress.
* The system may still show activity in logs.
* The failure is lack of completion, not lack of motion.

* Before and after test output.

== Trade-Offs
[.stretch]
[cols="1,1,1,1", options="header", width="100%"]
|===
|Approach
|Strengths
|Weaknesses
|When to Use

|Simple baseline
|Easy to explain and implement
|Hides timing and pressure assumptions
|First implementation and comparison point

|Guarded state transition
|Protects the invariant directly
|Requires careful state modeling
|Workflow steps and status changes

|Explicit coordination
|Makes dependencies visible
|Can introduce waiting or deadlock
|Multi-object ordering requirements

|Idempotent retry-safe design
|Handles duplicates and partial failure
|Needs keys and deduplication
|Queues, retries, external calls

|Observability-first design
|Produces strong evidence
|Adds instrumentation work
|Assignments requiring proof
|===

== Practical Steps
* Write the invariant first.
* Write one happy-path test.
* Write one pressure test.
* Add operation IDs and entity IDs.
* Compare before and after behavior.
* Record the remaining risk in the Integrity Packet.

== Summary
* Blocking and non-blocking are coordination choices, not just API styles.
* The real question is whether progress remains observable under pressure.
* Good design makes the invariant explicit.
* Good evidence makes the claim defensible.
