== Failure Scenario

* Overlapping execution may result in stale state.
* Mismatch between design assumption and execution model.

== Improved Design Direction

* Name invariant and make transitions observable.
* Implement controls: version checks, idempotency keys, etc.

== Why Improved Design?

* Moves from hoping execution order to proving invalid interleavings are handled.

== Failure Modes and Anti-Patterns

== Symptom: Single happy-path demonstration succeeds

* Detection: Add concurrent actors or stress tests.
* Correction: Add failure-focused test targeting invariant.

== Symptom: Names a tool, not a design property

* Detection: Ask which invariant the mechanism protects.
* Correction: Write invariant first, then select mechanism.

== Symptom: Evidence too vague to support claims

* Detection: Reviewer cannot reconstruct failure.
* Correction: Capture structured evidence linked to design claim.

== Symptom: Fix changes behavior without baseline comparison

* Detection: No before/after using same workload.
* Correction: Keep failing test and rerun after redesign.

== Trade-Off Analysis

[cols="1,1,1,1", options="header"]
|===
| Approach | Strengths | Weaknesses | When to Use
| Simple baseline | Easy to explain | Hides timing assumptions | First implementation
| Guarded state | Protects core invariant | Needs careful modeling | Status changes
| Explicit coordination | Makes dependencies visible | May cause deadlock | Multi-object workflows
| Idempotent design | Handles duplicates | Requires side-effect control | Queues, retries
| Observability-first | Strong evidence | Adds instrumentation | Assignments requiring proof
|===

== Practical Application

* Identify relevant invariant for simplicity vs. scalability.
* Write sequential scenario that should succeed.
* Write pressure scenario that could expose failure.
* Add operation IDs to logs before pressure scenario.
* Capture before/after evidence if applying a fix.
