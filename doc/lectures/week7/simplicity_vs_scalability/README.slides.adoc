== Simplicity, Pressure, and Evidence

* Simple designs can look correct on the happy path
* Pressure reveals timing, coordination, and state assumptions
* The key question is what invariant must remain true
* Evidence must be repeatable, structured, and tied to the claim
* The fix should protect the invariant, not hide the trade-off

== Trade-Offs

[.stretch]
[cols="1,1,1,1", options="header", width="100%"]
|===
|Approach |Strength |Weakness |Best Use

|Simple baseline
|Easy to explain
|Hides pressure assumptions
|First pass

|Guarded transition
|Protects the invariant
|Requires state modeling
|Status changes

|Explicit coordination
|Makes dependencies visible
|Can bottleneck
|Multi-step workflows

|Observability-first
|Strong evidence
|Instrumentation cost
|Assignments with proof
|===

== Practical Steps

* Identify the invariant or progress property
* Write one sequential success scenario
* Write one pressure scenario that can fail
* Add operation IDs and entity IDs to logs
* Capture before and after evidence
* Defend the trade-off in the Integrity Packet
