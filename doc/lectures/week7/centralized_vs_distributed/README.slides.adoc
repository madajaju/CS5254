== Opening Narrative

* Components wait for one another
* Logs show activity, workflow incomplete
* Coordination contract is incomplete
* Key design rule: How to ensure observable progress?

== Coordination Boundary

* Definition: Where independent objects agree
* Importance: Must be explicit under pressure
* Mechanisms: State, timing, behavior, retries
* Failure: Ignoring leads to duplicate work, stale state
* Implication: Expose invariant, validate with tests

== Progress Guarantee

* Definition: Ensures work completes eventually
* Importance: Trustworthiness under pressure
* Mechanisms: Same as Coordination Boundary
* Failure: Ignoring leads to same issues
* Implication: Expose invariant, validate with tests

== Contention

* Definition: Competition for shared resources
* Importance: Must be explicit under pressure
* Mechanisms: Same as previous concepts
* Failure: Same issues arise if ignored
* Implication: Expose invariant, validate with tests

== Worked Example

* Problem setup: Podcast domain, centralized vs. distributed
* Naive design assumption: operation executes once

== Naive Implementation

```text
actor performs operation
system reads current state
system applies transition
system emits side effect
```

== Failure Scenario

* Overlapping execution leads to stale state
* Issues: late execution, stuck workflows
* Problem: Mismatch between design and execution

== Corrected Design Direction

* Name the invariant, make transitions observable
* Add correctness controls: version checks, idempotency keys
* Focus on proven interleavings containment

== Failure Modes and Anti-Patterns

* Happy-path detection: tests avoid pressure conditions
  * Correction: Add targeted failure-focused tests
* Vague evidence leads to weak claims
  * Correction: Capture structured evidence
* Changes without baseline comparison
  * Correction: Preserve repeatable scenarios

== Trade-Off Analysis

[cols="1,1,1,1", options="header"]
|===
| Approach | Strengths | Weaknesses | When to Use
| Simple baseline | Easy to explain | Hides timing assumptions | First implementation
| Guarded state transition | Protects core invariant | Requires careful modeling | Status changes
| Explicit coordination | Makes dependencies visible | Risks waiting or deadlock | Multi-object workflows
| Idempotent design | Handles duplicates | Needs keys or deduplication | Queues, retries
| Observability-first | Strong evidence | Adds instrumentation | Requires failure proof
|===
