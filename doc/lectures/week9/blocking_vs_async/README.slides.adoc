== Concept: Blocking Call
* Thread waits for a response
* Must be explicit for system trust
* Mechanism: state, timing, behavior
* Failure: duplicates, stale state, progress blocked
* Design: expose invariant; validate behavior

== Worked Example: Problem Setup
* Podcast Domain: Orchestrator waits for AudioCleaner
* Order System: Waiting for external Payment Gateway
* Example of blocking under load

== Worked Example: Naive Implementation
* Assumes one operation, in order
* Often invisible in code
* Sequential test passes

== Worked Example: Failure Scenario
* Operations can observe stale state
* Execute twice; arrive late
* Mismatch between design and execution

== Worked Example: Improved Design
* Name invariant and make transition observable
* Add correctness controls: version checks, etc.
* Moves from hope to proof

== Failure Modes and Anti-Patterns
* **Symptom**: Single happy-path test passes
  * **Detection**: Add concurrent actors, stress conditions
  * **Correction**: Add failure-focused tests
* **Symptom**: Names tools, not properties
  * **Detection**: Ask which invariant is protected
  * **Correction**: State invariant first, then mechanism

== Trade-Off Analysis
[cols="1,1,1,1", options="header"]
|===
| Approach | Strengths | Weaknesses | When to Use
| Simple baseline | Easy to explain | Hides timing assumptions | First implementation
| Guarded state | Protects core invariant | Needs modeling | Status changes
| Explicit coordination | Makes dependencies visible | Can introduce bottlenecks | Multi-object workflows
| Idempotent design | Handles duplicates | Requires control | Queues, retries
| Observability-first | Strong evidence | Adds work | Assignments requiring proof
|===
