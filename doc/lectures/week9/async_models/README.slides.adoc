== Naive Model

[.column]
* Operation happens once
* State is current
* Order is guaranteed
* Sequential test passes

[.column]
* Hidden timing assumption
* Retry or delay breaks it
* Duplicate work appears
* State becomes stale

== Corrected Design

[.column]
* Name the invariant
* Expose the transition
* Add idempotency or version checks

[.column]
* Add coordination or retries
* Log critical IDs and states
* Validate with repeatable tests

== Failure Modes and Anti-Patterns

* Symptom: The system passes a single happy-path demonstration.
  * Why it happens: The test avoids the timing, ordering, or pressure condition.
  * How to detect it: Add repeated runs, concurrent actors, delayed events, or stress.
  * How to correct it: Keep the happy-path test and add a failure-focused test.

== Failure Modes and Anti-Patterns (cont)

* Symptom: The explanation names a tool but not a design property.
  * Why it happens: Students focus on frameworks before invariants.
  * How to detect it: Ask which invariant the mechanism protects.
  * How to correct it: Write the invariant first, then select the mechanism.

== Failure Modes and Anti-Patterns (cont)

* Symptom: Evidence is too vague to support the claim.
  * Why it happens: Logs lack operation IDs or state transitions.
  * How to detect it: A reviewer cannot reconstruct the failure.
  * How to correct it: Capture structured evidence and link it to the claim.

== Trade-Off Analysis

[.stretch]
[cols="1,1,1,1", options="header", width="100%"]
|===
|Approach |Strengths |Weaknesses |When to Use
|Simple baseline |Easy to explain and implement |Hides timing and pressure assumptions |First implementation and comparison point
|Guarded state transition |Protects the core invariant directly |Requires careful state modeling |Status changes, reservations, workflow steps
|Explicit coordination |Makes dependencies visible |Can introduce waiting or bottlenecks |Multi-object workflows with ordering requirements
|Idempotent or retry-safe design |Handles duplicate work and partial failure |Requires keys or side-effect control |Queues, retries, external calls, async workers
|Observability-first design |Produces strong evidence for review |Adds instrumentation work |Assignments requiring failure proof and defense
|===

== Validation and Interview Questions

* What invariant or progress property is most relevant?
* What hidden assumption makes the baseline appear correct?
* How would you force the failure in a repeatable test?
* What evidence would prove the failure occurred?
* Which design mechanism would you choose first?
* What trade-off does it introduce?
* How would the same issue appear in your two stacks?
* What would you record in the Integrity Packet?

== Summary

The central insight is that async models across languages is not just a vocabulary item; it is a way to reason about whether a system remains correct under realistic execution. The professional engineering task is to connect the concept to invariants, observable behavior, and defensible trade-offs. A design is not mature until it can be explained, stressed, repaired, and validated with evidence.
