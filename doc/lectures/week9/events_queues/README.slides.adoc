== Naive Implementation

* Assumes one-time operation
* Current state reliance
* Simplicity hides complexity

```text
actor performs operation
system reads current state
system applies transition
system emits side effect
```

== Failure Scenario

* Overlapping execution and delays
* Stale state, late arrivals, workflow stuck
* Mismatch between design assumptions and execution

== Improved Design Direction

* Name and expose the invariant
* Make transitions observable
* Control correctness with retries, version checks

== Why Improved Design is Safer

* Changes focus from hope to proof
* Rejection or recovery of invalid interleavings with evidence

== Failure Modes & Anti-Patterns

* Symptom: Single happy-path test
  * Detection: Add concurrent tests
  * Correction: Include failure-focused tests

* Symptom: Tool naming, not design property
  * Detection: Ask about invariant protection
  * Correction: Define invariant first

* Symptom: Vague evidence
  * Detection: Reviewer cannot reconstruct failure
  * Correction: Capture structured evidence

* Symptom: Uncompared fixes
  * Detection: No repeatable baseline run
  * Correction: Preserve failing test

== Trade-Off Analysis

[cols="1,1,1,1", options="header"]
|===
| Approach | Strengths | Weaknesses | When to Use
| Simple baseline | Easy implementation | Hides assumptions | First implementation
| Guarded state transition | Protects invariant | Requires careful modeling | Status changes
| Explicit coordination | Makes dependencies visible | May cause bottlenecks | Multi-object workflows
| Idempotent design | Handles duplicates | Needs control | Queues and async workers
| Observability-first | Strong evidence | Adds instrumentation | Assignments needing proof
|===
