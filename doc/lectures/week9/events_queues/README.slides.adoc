= Events, Queues, Workers

== Opening Narrative

* A synchronous workflow is moved into background workers to improve responsiveness.
* The user no longer waits, but correctness now depends on events, retries, ordering, and observability.
* The design has changed even if the business workflow sounds the same.
* What must be made explicit when work moves across time?

== Trade-Off Table

[.stretch]
[cols="1,1,1,1", options="header", width="100%"]
|===
|Approach |Strengths |Weaknesses |When to Use
|Simple baseline |Easy to explain and implement |Hides timing assumptions |First comparison point
|Guarded state transition |Protects the core invariant directly |Requires careful state modeling |Workflow steps and status changes
|Explicit coordination |Makes dependencies visible |Can add waiting or bottlenecks |Ordering-sensitive workflows
|Idempotent design |Handles duplicate work and retries |Needs keys and deduplication |Queues and external side effects
|===

== Practical Application

* Identify the invariant or progress property most relevant to events, queues, workers.
* Write one sequential scenario that should succeed.
* Write one pressure scenario that could expose the failure.
* Add operation IDs and entity IDs to the logs before running the pressure scenario.
* Capture before and after evidence if you apply a fix.
* Update the Integrity Packet with the assumption, evidence, validation, and remaining risk.
