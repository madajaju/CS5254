== Naive Implementation

A naive design assumes:

* Operation happens once, in order, and with current state
* Often invisible in code due to method naming

```text
actor performs operation
system reads current state
system applies transition
system emits side effect
```

== Failure Scenario

* Overlapping execution leads to stale state, retries
* Failure is not just syntax errors; reflects design mismatch

== Improved Design Direction

* Name the invariant explicitly
* Make transitions observable
* Use keys, guards, retries with backoff, etc.

== Safer Design Explanation

Switching from:
* Hopeful execution order
To:
* Proving invalid interleavings are contained or recovered

== Failure Modes and Anti-Patterns

* Symptom: Passes happy-path test
  * **Detection**: Run under pressure
  * **Correction**: Add failure-focused tests

* Symptom: Names tools, not design properties
  * **Detection**: Ask about the invariant
  * **Correction**: Define invariant first

* Symptom: Vague evidence
  * **Detection**: Reviewer cannot reconstruct failure
  * **Correction**: Capture structured evidence

* Symptom: Fix changes behavior, no baseline
  * **Detection**: Lack of before/after tests
  * **Correction**: Keep failing test for comparison

== Trade-Off Analysis

[cols="1,1,1,1", options="header"]
|===
| Approach | Strengths | Weaknesses | When to Use
| Simple baseline | Easy to explain | Hides timing assumptions | First implementation
| Guarded state | Protects invariant | Needs careful modeling | Status changes 
| Explicit coordination | Visible dependencies | Can cause deadlock | Multi-object workflows 
| Idempotent design | Handles duplicates | Requires keys | Async workers
| Observability-first | Strong evidence | Adds instrumentation | Design proof
|===
