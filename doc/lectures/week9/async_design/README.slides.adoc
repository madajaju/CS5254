= Designing Async Systems

== Opening Pressure

[.column]
* A synchronous workflow moves to background workers
* Responsiveness improves
* Correctness now depends on events, retries, ordering, observability

[.column]
* The business workflow looks the same
* The execution model changes
* The question becomes: what must be explicit across time?

== Core Concepts

* Event storming makes significant events explicit
* Workflow orchestration names the async control point
* Error propagation must work without a waiting user
* Observability depends on correlation IDs and structured traces

== Design Controls

[.column]
* Invariant first
* Then choose a control
* Version checks
* Idempotency keys

[.column]
* Durable completion records
* Retry with backoff
* Compensation or reconciliation
* Structured logs with IDs

== Trade-Offs

[.stretch]
[cols="1,1,1,1", options="header", width="100%"]
|===
|Approach |Strengths |Weaknesses |Use When

|Simple baseline
|Easy to explain
|Hides timing assumptions
|First pass and comparison

|Guarded state transition
|Protects the invariant directly
|Needs careful state modeling
|Status changes and workflow steps

|Explicit coordination
|Makes dependencies visible
|Can bottleneck progress
|Multi-object ordering requirements

|Idempotent retry-safe design
|Handles duplicates and partial failure
|Needs keys or deduplication
|Queues and external calls
|===
