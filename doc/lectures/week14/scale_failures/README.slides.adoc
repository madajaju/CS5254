== Linear vs. Non-Linear Scaling

* Definition: Doubling work > double time/resources.
* Why it matters: Trust under pressure.
* Mechanism: Object state, workflow timing.
* Failure mode: Duplicate work, stale state.
* Design implication: Log transitions, validate behavior.

== Single Point of Contention

* Mechanism: Object states, workflow timing.
* Failure mode: Duplicate work, blocked progress.

== Naive Implementation

* Assumption: Operations happen once and in order.
* Implementation reasoning may be invisible.
* Sequence of operations:
** Actor performs operation.
** System reads current state.
** Applies transition.
** Emits side effect.

== Failure Scenario

* Overlapping execution may:
** Observe stale state.
** Execute twice.
** Cause workflow to stall.
* Failure highlights design versus execution mismatch.

== Corrected Design Direction

* Name the invariant.
* Make transitions observable.
* Add correctness controls:
** Version checks.
** Idempotency keys.
** Explicit coordination.

== Improved Design Safety

* Changes problem from execution hope to proof of:
** Invalid interleavings being rejected.
** Evidence of recovery process.

== Failure Modes and Anti-Patterns

* Happy-path system passes tests.
  * Why: Tests avoid pressure conditions.
  * Detect: Concurrent tests or structured logs.
  * Correct: Add failure-focused tests.

* Explanation misses design property.
  * Why: Focus on tools not properties.
  * Detect: Ask for the invariant.
  * Correct: State invariant before mechanism.

* Vague evidence lacks detail.
  * Why: Logs lack IDs or transitions.
  * Detect: Reviewer cannot reconstruct failure.
  * Correct: Capture structured evidence.

* Fix changes behavior unnoticed.
  * Why: No preserved repeatable scenario.
  * Detect: Missing before/after runs.
  * Correct: Keep failing tests for reruns.

== Trade-Off Analysis

[cols="1,1,1,1", options="header"]
|===
| Approach | Strengths | Weaknesses | When to Use
| Simple baseline | Easy implementation | Hides assumptions | First comparison point
| Guarded state transition | Protects invariant | Requires modeling | Status changes
| Explicit coordination | Shows dependencies | Can introduce delays | Multi-object workflows
| Idempotent design | Handles duplicates | Needs deduplication | Async tasks, retries
| Observability-first | Strong evidence | Adds workload | Assignments requiring defense
|===
