== Objectives

* Analyze design pressure in concurrent systems
* Diagnose hidden assumptions in system behavior
* Evaluate logs, traces, and test outputs
* Design corrections that preserve invariants
* Defend approach in Integrity Packet

== Opening Narrative

* A project appears correct initially.
* Concurrency or pressure reveals hidden assumptions.
* What must be defended before trusting the result?

== Design Justification

* *Why* behind a decision, not just *How*.
* Identifies critical conditions for trust under pressure.
* Ignoring assumptions leads to stale state and blocked progress.
* Must expose relevant invariant and validate with tests.

== Handling Challenges

* Respond to "Why not use a global lock?".
* Conditions for trust must be explicit.
* Missing critical transitions leads to misleading evidence.
* Implementation must validate behavior through evidence.

== Evidence-First Defense

* Use stress test logs as your primary defense.
* Identifies explicit conditions necessary for trust.
* Vague evidence won’t support claims.
* Design needs visible invariants and structured tests.

== Acknowledging Limits

* Identify where design won’t work.
* Builds credibility in your defense.
* Ignoring limits creates misleading happy paths.
* Write invariants first, then select mechanisms.

== System Invariant

* Condition must remain true across executions.
* Lack of clarity on invariants undermines trust.
* Can lead to duplicate work or progressive states.
* Expose invariants and validate behavior through tests.

== Worked Example

== Problem Setup

* **Podcast Domain**:
* *Challenge*: Async queue could lose messages.
* *Defense*: Reconciliation Job every 5 minutes to re-queue lost episodes.

== Naive Implementation

[.code]
----
actor performs operation
system reads current state
system applies transition
system emits side effect
----

== Failure Scenario

* Stale state or duplicate execution.
* Not mere syntax bugs; reveal mismatched assumptions.

== Improved Design Direction

* Name the invariant.
* Observe transitions and add correctness controls:
** Version checks
** Idempotency keys
** State-machine guards

== Failure Modes

* Symptom: Passes happy path only.
** Detection: Use stress tests.
* Symptom: Tool names without design properties.
** Detection: Ask about protected invariants.
* Symptom: Vague evidence.
** Detection: Inability to reconstruct failures.
* Symptom: Behavior changes without baseline comparison.
** Detection: No repeatable tests available.

== Trade-Off Analysis

[cols="1,1,1,1", options="header"]
|===
| Approach | Strengths | Weaknesses | When to Use
| Simple baseline | Easy to implement | Hides assumptions | First comparison
| Guarded state transition | Protects invariants | Requires state modeling | Workflow changes
| Explicit coordination | Visualizes dependencies | Risk of deadlock | Multi-object workflows
| Idempotent design | Handles duplicates | Needs control | Queues, async tasks
| Observability-first | Strong evidence | Adds instrumentation | Failure proof tasks
|===
