== Core Concept: System Integrity

* Definition: Maintains invariants and data consistency under pressure.
* Importance: Must be made explicit to trust the system.
* Mechanism: Appears through state, timing, behavior, retries.
* Failure Mode: Can produce duplicates, staleness, or misleading evidence.
* Design Implication: Log transitions, validate behavior, expose invariants.

== Integrity Chain

* Definition: Connection of object boundaries and management.
* Importance: Must be made explicit to trust the system.
* Mechanism: Shown through state, timing, worker behavior, coordination.
* Failure Mode: Same as before, leading to misunderstandings.
* Design Implication: Same as before, ensuring evidence and validation.

== System Invariant

* Definition: Must remain true across all valid executions.
* Importance: Essential for trust under pressure.
* Mechanism: Evident through workflows and timing.
* Failure Mode: Leads to duplicates and state issues.
* Design Implication: Log behavior and validate transitions.

== Failure Mode

* Definition: Repeatable ways the system violates invariants.
* Importance: Clear understanding is required to build trust.
* Mechanism: Evident in object states and coordination aspects.
* Failure Mode: Similar consequences as previous.
* Design Implication: Ensure log and validation processes.

== Design Trade-Off

* Definition: Choices between simplicity, safety, and performance.
* Importance: Affects trustworthiness under pressure.
* Mechanism: Influences through state management and timing.
* Failure Mode: Similar breakdowns may occur.
* Design Implication: Ensure clarity on invariants within designs.

== Worked Example: Problem Setup

* **Podcast Domain**:
  * `Cleaner` may fail, but `Orchestrator` retries.
  * `IdempotencyKey` prevents duplicates ensuring correct state.

* **Validation**:
  * Logs demonstrate "Zero Invariant Violations" during stress tests.

== Naive Implementation

* Assumes linear execution and current state validity.
* Execution steps may mislead because:
  * Method names seem correct.
  * Sequential tests pass.

== Failure Scenario

* Overlapping executions lead to stale states or duplicates.
* Failures reveal mismatches between assumptions and execution.

== Corrected Design Direction

* Name the invariant, observe transitions.
* Appropriate controls:
  * Version checks, state guards, retries.
  * Coordination or reconciliation techniques.

== Why the Improved Design Is Safer

* Shifts focus from execution hope to proving order and evidence of correct state.

== Failure Modes and Anti-Patterns

* Symptom: Happy-path passes but lacks pressure.
  * Detect by revisiting logs: structure tests around timing.
  
* Symptom: Tools used without stating design properties.
  * Identify mechanisms protecting specific invariants.

* Symptom: Vague evidence without sufficient detail.
  * Structure logs to reconstruct failures effectively.

* Symptom: Fix alters behavior untracked against the baseline.
  * Ensure repeatable tests remain post-fix.

== Trade-Off Analysis

[cols="1,1,1,1", options="header"]
|===
| Approach | Strengths | Weaknesses | When to Use
| Simple baseline | Explained easily | Hides timing assumptions | Initial implementation
| Guarded transition | Direct invariant protection | State modeling required | Status changes
| Explicit coordination | Shows dependencies | Risk of deadlock | Multi-object workflows
| Idempotent design | Handles duplicates | Requires deduplication | External calls
| Observability-first | Strong evidence | Adds instrumentation | Validating failure
|===
