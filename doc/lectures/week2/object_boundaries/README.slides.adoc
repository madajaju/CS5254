== Worked Example
* Podcast Domain: `Episode` object owns its `Status`.
* Bad Design: Global `Map<EpisodeId, Status>` modified by any part of the system.

=== Naive Implementation
```text
actor performs operation
system reads current state
system applies transition
system emits side effect
```

== Failure Scenario
* Overlapping execution can observe stale state or execute twice.
* The failure is a mismatch between design assumption and execution model.

== Corrected Design Direction
* Name invariant, make transition observable.
* Add version checks or explicit coordination.

== Why the Design Is Safer
* Proves invalid interleavings are rejected or recovered with evidence.

== Trade-Off Analysis
[.stretch]
[cols="1,1,1,1", options="header"]
|===
| Approach | Strengths | Weaknesses | When to Use
| Simple baseline | Easy to explain and implement | Hides timing assumptions | First implementation and comparison point
| Guarded state transition | Protects core invariant | Requires careful state modeling | Status changes, reservations, publishing
| Explicit coordination | Makes dependencies visible | Can introduce deadlocks | Multi-object workflows with ordering
| Idempotent design | Handles duplicate work | Requires deduplication | Queues, retries, async workers
| Observability-first design | Produces strong evidence | Adds instrumentation work | Assignments requiring failure proof
|===

== Practical Application
* Identify invariant or progress property.
* Write sequential scenario that should succeed.
* Write pressure scenario to expose failure.
* Add operation IDs and entity IDs to logs.
* Capture before/after evidence if applying a fix.
* Update Integrity Packet with assumption, evidence, validation.

== Assignment Integration
* Connect lecture concept to A1.
* Show relevant object, workflow, event, or recovery mechanism.

== Validation Questions
* What invariant is most relevant?
* What hidden assumption could make design appear correct?
* How would you force the failure in a test?
* What evidence would prove failure occurred?
* Which design mechanism to choose first, and what trade-off does it introduce?
* How would issue appear in different implementation stacks?
* What to record in Integrity Packet?

== Summary
* Object boundaries & responsibilities check if systems remain correct under execution.
* Connect concept to invariants, observable behavior, and defensible trade-offs.
* Design must be explained, stressed, repaired, and validated with evidence.
