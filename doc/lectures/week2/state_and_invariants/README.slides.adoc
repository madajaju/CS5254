= State & Invariants

== Learning Objectives
* Analyze the design pressure of state & invariants in concurrent systems.
* Diagnose assumptions making the system appear correct.
* Evaluate failure evidence: logs, traces, interleavings, test outputs.
* Design corrections preserving relevant invariants; disclose trade-offs.
* Defend approaches in the Integrity Packet; relate to A1 deliverables.

== Opening Narrative
* A course project appears correct during a demonstration.
* Concurrency or operational pressure reveals hidden assumptions.
* What must the engineer analyze to trust the result?

== Core Concepts

== System State
* Definition: Collective values of data at a point in time.
* Mechanism: Revealed through object state, timing, behavior.
* Failure mode: Ignoring leads to duplicate work, stale state.
* Design implication: Log transitions and validate behaviors.

== Invariants
* Definition: Conditions that must *always* hold true for correctness.
* Mechanism: Revealed through object state, timing, behavior.
* Failure mode: Ignoring can lead to duplicate work, stale state.
* Design implication: Log transitions and validate behaviors.

== State Transitions
* Definition: Valid paths changing the system from one state to another.
* Mechanism: Revealed through object state, timing, behavior.
* Failure mode: Ignoring can lead to duplicate work, stale state.
* Design implication: Log transitions and validate behaviors.

== Invariant Violation
* Definition: Concurrent operations causing impossible states.
* Mechanism: Revealed through object state, timing, behavior.
* Failure mode: Ignoring can lead to duplicate work, stale state.
* Design implication: Log transitions and validate behaviors.

== System Invariant
* Definition: Conditions remaining true across valid executions.
* Mechanism: Revealed through object state, timing, behavior.
* Failure mode: Ignoring leads to duplicate work, stale state.
* Design implication: Log transitions and validate behaviors.

== Failure Modes and Anti-Patterns
* Symptom: System passes a single happy-path demo.
* Symptom: Explanation names a tool, not a design property.
* Symptom: Evidence is too vague to support claims.
* Symptom: Fix changes behavior; not compared to baseline.

== Trade-Off Analysis
[.stretch]
[cols="1,1,1,1", options="header"]
|===
| Approach | Strengths | Weaknesses | When to Use |
| Simple baseline | Easy to explain | Hides timing assumptions | Initial implementation |
| Guarded state transition | Protects core invariant | Requires careful modeling | Status changes |
| Explicit coordination | Makes dependencies visible | Can create deadlocks | Multi-object workflows |
| Idempotent design | Handles duplicates | Requires keys | Queuing |
| Observability-first | Strong evidence | Adds instrumentation | Failure proof assessments |
|===
