== Core Concepts
== Structured Logging
* Definition: Logging in a machine-readable format (like JSON) that includes metadata like timestamps, thread IDs, and levels.
* Failure mode: If ignored, the system can produce duplicate work or stale state.

== Correlation IDs
* Definition: A unique ID assigned to a specific request or workflow that travels through all logs generated by that operation.
* Failure mode: If ignored, the system can produce duplicate work or stale state.

== Traceability
* Definition: The ability to see the exact sequence of events for a single object across different threads.
* Failure mode: If ignored, the system can produce duplicate work or stale state.

== Observability
* Definition: Building the system so that its internal state can be understood by looking at its external outputs (logs).
* Failure mode: If ignored, the system can produce duplicate work or stale state.

== Operational Pressure
* Definition: Load, latency, volume, or failure conditions that reveal hidden system limits.
* Failure mode: If ignored, the system can produce duplicate work or stale state.

== Failure Scenario
* Under overlapping execution, delayed delivery, or partial failure, the same operation can observe stale state or duplicate effects.
* The failure is a mismatch between the design assumption and the execution model.

== Evidence Flow
* Claim: Structured Logging & Observability is defensible when the design shows both the failure and the recovery path with measurements.
* Decision: Accept a design only when its stress evidence includes baseline, failure, correction, and residual risk.

== Failure Modes and Anti-Patterns
* Symptom: The system passes a single happy-path demonstration.
  * How to correct: Add a failure-focused test targeting the invariant.
* Symptom: The explanation names a tool but not a design property.
  * How to correct: State the invariant first, then select the mechanism.
* Symptom: Evidence is too vague to support the claim.
  * How to correct: Capture structured evidence linked to the design claim.

== Trade-Off Analysis
[.stretch]
[cols="1,1,1,1", options="header"]
|===
| Approach | Strengths | Weaknesses | When to Use
| Simple baseline | Easy to explain and implement | Hides timing and pressure assumptions | First implementation
| Guarded state transition | Protects core invariant directly | Requires careful modeling | Status changes
| Explicit coordination | Makes dependencies visible | Can introduce deadlock | Multi-object workflows
| Idempotent design | Handles duplicates | Requires keys | Queues, retries
| Observability-first | Strong evidence produced | Adds instrumentation work | Assignments requiring proof
|===
