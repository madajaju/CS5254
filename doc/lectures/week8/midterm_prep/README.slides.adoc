== Worked Example
* Exam Style Question: "Thread A runs `x = x + 1`, Thread B runs `x = x + 2`. Possible final values?"
* Naive Implementation: Assumes sequential execution with current state.

== Failure Scenario
* Under overlapping execution:
** Potential issues from stale state.
** Operation may execute multiple times or arrive late.

== Improved Design Direction
* Name the invariant.
* Make transitions observable.
* Add correctness controls:
** Version checks, idempotency keys, retries.

== Why Improved Design
* Shift focus from hoping for execution order to proving invalid interleavings are contained.

== Failure Modes and Anti-Patterns
* System passes single happy-path test.
** Detection: Use multiple runs, structured logs.

* Explanation names a tool, not a design property.
** Detection: Ask which invariant is protected.

* Evidence too vague to support claims.
** Detection: Reviewer cannot reconstruct failure.

* Fix changes behavior without comparison.
** Detection: No repeatable scenario exists.

== Trade-Off Analysis
[cols="1,1,1,1", options="header"]
|===
| Approach | Strengths | Weaknesses | When to Use
| Simple baseline | Easy to explain | Hides timing assumptions | First implementation
| Guarded transition | Protects core invariant | Requires careful modeling | Status changes
| Explicit coordination | Makes dependencies visible | Can introduce bottlenecks | Multi-object workflows
| Idempotent design | Handles duplicates | Requires deduplication | Queues, retries
| Observability-first | Strong evidence | Adds instrumentation | Needs failure proof
|===
