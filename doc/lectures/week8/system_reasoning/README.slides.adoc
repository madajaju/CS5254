== Core Concepts

== Deductive Reasoning

* Definition: Use observations to prove internal behavior.
* Importance: Identifies conditions to trust the system under pressure.
* Mechanism: Observed through states, timing, behavior.
* Failure mode: Can lead to duplicate work or misleading evidence.
* Implication: Expose invariants, log transitions, validate tests.

* Definition: Conceptual map of execution without code.
* Importance: Identifies conditions to trust the system under pressure.

== Hypothesis Testing

* Definition: Theory on a failure, tested to prove/disprove.
* Importance: Identifies conditions to trust the system under pressure.
* Mechanism: Appears through states, timing, retries.
* Failure mode: Yield duplicate work or misleading logs if ignored.
* Implication: Expose invariants, log transitions, validate tests.

* Importance: Identifies conditions to trust the system under pressure.

* Failure mode: Leads to misleading evidence or loss of progress.
* Implication: Expose invariants, log transitions, validate tests.

== Worked Example

== Problem Setup

* Live Analysis: Logs show `Episode-1` published twice.
** Observation: Thread A logs "Checking status" at 10.01ms.
** Observation: Thread B logs "Checking status" at 10.02ms.
** Deduction: No locking between check and update.

* Project Context: Applying reasoning to a student's project.

== Mental Model

Assuming operation happens once, in order, and with the current state:

```text
actor performs operation
system reads current state
system applies transition
system emits side effect
```

== Failure Scenario

Competing executions under pressure can yield stale states or duplicate operations. This mismatch reveals design assumptions versus actual execution.

== Improved Design Direction

Name the invariant, make transitions observable, and implement controls: version checks, idempotency, coordination mechanisms, or retries.

== Why Is It Safer?

The improved design shifts focus from trusting execution order to proving that invalid conditions are contained or recoverable with evidence.

== Failure Modes

== Happy-path Success

* Symptom: Happy-path success in tests.
* Cause: Tests avoid timing or pressure conditions.
* Detection: Introduce repeated runs and concurrency.
* Correction: Add failure-focused tests targeting invariants.

== Naming Tools

* Symptom: Naming tools without design properties.
* Cause: Ignore stating invariants.
* Detection: Ask which invariant is protected.
* Correction: Write invariant first, then choose mechanisms.

== Vague Evidence

* Symptom: Vague evidence supporting claims.
* Cause: Logs lacking critical identifiers.
* Detection: Reviewers cannot trace failure from evidence.
* Correction: Capture structured evidence linked to claims.

== Trade-Off Analysis

[cols="1,1,1,1", options="header"]
|===
| Approach | Strengths | Weaknesses | When to Use
| Simple baseline | Easy to explain | Hides timing assumptions | First implementation
| Guarded state | Protects invariant | Requires modeling | Status changes
| Explicit coordination | Makes dependencies clear | May cause deadlock | Multi-object workflows
| Idempotent design | Handles duplicates | Needs deduplication | Queues, async workers
| Observability-first | Strong evidence | Adds instrumentation overhead | Design defenses
|===
