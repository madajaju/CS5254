== Core Concept: Race Condition (Lost Update)

* Definition: Multiple writers, no protection
* Mechanism: Through state, timing, behavior
* Failure: Duplicate work, stale state

== Core Concept: Race Condition (Check-Then-Act)

* Definition: Reads stale state before deciding
* Mechanism: Through state, timing, behavior
* Failure: Duplicate work, stale state

== Core Concept: Deadlock

* Definition: Circular resource dependency
* Mechanism: Through state, timing, behavior
* Failure: Stalled progress

== Core Concept: Missed Signal

* Definition: Signaling an object not in "waiting"
* Mechanism: Through state, timing, behavior
* Failure: Stalled progress

== Core Concept: Livelock

* Definition: Active but futile state changes
* Mechanism: Through state, timing, behavior
* Failure: Misleading evidence

== Naive Implementation

* Assumes operation happens once and in order
* Invisible assumptions in code
* Example logic:
** Actor performs operation
** System reads state
** System applies transition
** System emits effect

== Failure Scenario

* Overlapping execution or retries
* Same operation can observe stale state
* Not just a syntax bug
* Mismatch: design assumption versus execution model

== Corrected Design Direction

* Name the invariant
* Make transition observable
* Add correctness control:
** Version checks, idempotency keys
** State-machine guards, retries with backoff

== Why Improved Design is Safer

* Proves invalid interleavings are rejected
* Provides confidence in workflow integrity

== Failure Modes and Anti-Patterns

* Symptom: Passes single happy-path test
** Why: Test avoids timing, pressure conditions
** Detection: Add stress tests

* Symptom: Names a tool, not a design property
** Why: Focus on mechanisms over invariants
** Correction: Write invariant first

* Symptom: Evidence is vague or incomplete
** Why: Logs lack identifiers or transitions
** Correction: Capture structured evidence

* Symptom: Fix changes behavior without comparison
** Why: Failure not repeatable
** Correction: Preserve failing test for comparison

== Trade-Off Analysis

[cols="1,1,1,1", options="header"]
|===
| Approach | Strengths | Weaknesses | When to Use
| Simple baseline | Easy to explain | Hides timing assumptions | First implementation
| Guarded state transition | Protects invariants | Requires modeling | Status changes
| Explicit coordination | Makes dependencies visible | Can cause deadlock | Multi-object workflows
| Idempotent design | Handles duplicates | Needs deduplication | Queues, async workers
| Observability-first design | Strong evidence | Adds instrumentation | Assignments requiring proof
|===
