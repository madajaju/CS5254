== Core Concept: Exponential Backoff
* Definition: Increasing wait time between retries
* Why it matters: Explicit condition under pressure
* Mechanism: Through state, workflow timing, and retries
* Failure mode: Duplicate work or stale state if ignored
* Design implication: Expose invariant and log transitions

== Core Concept: Compensation (Rollback)
* Definition: Undoing a previous successful step
* Why it matters: Trustworthiness under pressure
* Mechanism: Through state and worker behavior
* Failure mode: Duplicate work or misleading evidence
* Design implication: Log transitions and validate behavior

== Core Concept: Dead Letter Queue (DLQ)
* Definition: Separate queue for failed messages
* Why it matters: Trustworthiness under pressure
* Mechanism: Through state and workflow timing
* Failure mode: Stale state or blocked progress if ignored
* Design implication: Log transitions and validation

== Core Concept: Circuit Breaker
* Definition: Stop requests to failing components
* Why it matters: Trustworthiness under pressure
* Mechanism: Through state and behavior timing
* Failure mode: Duplicate work if ignored
* Design implication: Log transitions and validate behavior

== Worked Example: Problem Setup
* Podcast Domain:
** Retry: `AudioCleaner` retries upload 3 times
** DLQ: Failed uploads moved to admin queue

** Compensation if item is out of stock after payment

== Worked Example: Naive Mental Model
* Assumes operation happens once, in order
* State transitions considered correct if named correctly
* Sequential tests may pass despite hidden issues

== Worked Example: Failure Scenario
* Overlapping execution can observe stale state
* Same operation may run twice or arrive late
* Failure: mismatch between design assumption and execution model

== Worked Example: Corrected Design Direction
* Name the invariant, make transitions observable
* Add controls: version checks, retries, compensation
* Change from hoping execution order to proving correctness

== Failure Modes and Anti-Patterns
* Symptom: Single happy-path demonstration
** Why: Tests avoid timing and pressure conditions
** Detect: Add repeated runs and structured logs
** Correct: Preserve tests, add failure-focused tests

* Symptom: Tool named, not design property
** Why: Focus on mechanisms, not invariants
** Detect: Ask what invariant is protected
** Correct: Write invariant before mechanism

== Trade-Off Analysis
[cols="1,1,1,1", options="header"]
|===
| Approach | Strengths | Weaknesses | When to Use
| Simple baseline | Easy to explain | Hides timing assumptions | First implementation
| Guarded state | Protects invariant | Requires careful modeling | Status changes
| Explicit coordination | Makes dependencies visible | Can introduce bottlenecks | Multi-object workflows
| Idempotent/retry-safe | Handles duplicates | Requires deduplication | Queues and retries
| Observability-first | Strong evidence for review | Adds instrumentation | Assignments requiring proof
|===
