* Design: Expose invariants, log transitions, validate behavior

== Naive Implementation

* Assumes operations happen once and in order
* Often invisible in code
* Simplistic flow:
    * Actor performs operation
    * System reads state
    * System applies transition
    * System emits side effect

== Failure Scenario

* Under concurrency: stale state, late execution, blocked workflow
* Not a syntax bug; design assumption mismatch

== Improved Design Direction

* Name invariant, observable transitions
* Add correctness controls:
    * Version checks, idempotency keys
    * Explicit coordination, retries

== Why Improved Design Is Safer

* Moves from hoping for correctness 
* Proves invalid interleavings are handled

== Failure Modes & Anti-Patterns

* Symptom: Single happy-path test passes
    * Why: Test avoids timing conditions
    * Detect: Use stress tests, concurrent actors
    * Correct: Add targeted failure tests

* Symptom: Tool mentioned, not design property
    * Why: Focus on mechanisms over invariants
    * Detect: Ask which invariant is protected

== Trade-Off Analysis

[cols="1,1,1,1", options="header"]
|===
| Approach | Strengths | Weaknesses | When to Use
| Simple baseline | Easy to implement | Hides timing assumptions | First implementation
| Guarded state | Protects core invariant | Requires careful modeling | Status changes
| Explicit coordination | Makes dependencies visible | Can introduce deadlocks | Multi-object workflows
| Idempotent design | Handles duplicates | Needs deduplication controls | Queues, retries
| Observability-first | Produces strong evidence | Adds instrumentation work | Design defense
|===
