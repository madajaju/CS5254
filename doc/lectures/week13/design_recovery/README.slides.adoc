= Designing for Recovery

== Opening Question

* A project can look correct in a simple demo
* Pressure reveals hidden assumptions
* The real task is to defend recovery, not just success

== Comparison of Approaches

[.stretch]
[cols="1,1,1,1", options="header", width="100%"]
|===
|Approach |Strength |Weakness |Best Use

|Simple baseline
|Easy to explain
|Hides pressure assumptions
|Starting point

|Guarded state transition
|Protects the invariant directly
|Requires careful modeling
|Workflow steps

|Idempotent retry-safe design
|Handles duplicates and partial failure
|Needs deduplication support
|Queues and async work

|Observability-first design
|Produces strong evidence
|Adds instrumentation work
|Assignments and review
|===

== Closing Summary

* Recovery design is about correctness under pressure
* Name the invariant before choosing the mechanism
* Use repeatable failure evidence to defend the fix
* Connect the result to the Integrity Packet
