== Runtime Variance
* Definition: Variations in scheduling and I/O handling
* Impact: Designs can fail differently
* Mechanisms: Threads, event loops, locks
* Failure mode: Misinterpreting design correctness
* Focus: Maintain invariant, ignore syntax

== Conceptual Parity
* Definition: Two stacks represent the same concepts
* Importance: Equivalence is crucial for meaningful comparison
* Mechanisms: Shared domain diagrams, test scenarios
* Failure mode: Non-equivalent workflows mislead
* Focus: Document parity before style differences

== Hidden Assumptions
* Definition: Unstated beliefs about execution specifics
* Impact: Different stacks reveal or hide assumptions
* Mechanisms: Execution order affects data races
* Failure mode: Concluding correctness from one stack
* Focus: Create overlap in test conditions

== Comparable Evidence
* Definition: Logs and outputs for behavior comparison
* Importance: Required evidence for A1 assignments
* Mechanisms: ID logs and state transitions
* Failure mode: Inconclusive evidence for failures tested
* Focus: Evidence format integral to strategy

== Worked Example
* Problem: Podcast system in Java and Node.js
* Key components: `Episode`, `AssetProcessor`, `PublishingManager`
* Constraint: Episode cannot publish until assets are ready

== Naive Mental Model
```javascript
async function publishEpisode(id) {
  const episode = await loadEpisode(id);
  if (episode.status === "READY_TO_PUBLISH") {
    await saveStatus(id, "PUBLISHED");
    await notifySubscribers(id);
  }
}
```

== Failure Scenario
* Concurrent requests load the same episode
* `await` causes stale reads
* Java exposes through threads, Node.js through async

== Improved Design Direction
* Conceptual fix: Atomic transition of states
* Procedure:
** publish(id):
*** attempt READY_TO_PUBLISH -> PUBLISHED
*** emit notification once if transition succeeds

== Failure Modes
* One stack passes due to sequential test calls
** Detect: Logs show non-overlapping operations
** Correct: Introduce concurrent conditions

* Implementations drift from shared model
** Detect: Differing responsibilities
** Correct: Maintain shared object parity

* Runtime behavior mistaken for design proof
** Detect: Explanations describe platform, not states
** Correct: Center answers on invariant

* Logs cannot be compared due to differences
** Detect: Absence of common operation IDs
** Correct: Define shared log schema

== Trade-Off Analysis
[cols="1,1,1,1", options="header"]
|===
| Approach | Strengths | Weaknesses | When to Use
| Java plus Node.js | Strong contrast between concurrency models | Requires careful async reasoning | Good default comparison
| Python plus Go | Contrasts interpreter constraints with concurrency | Misunderstand Python behavior | Worker-style tests
| Java plus Go | Strong primitives in both | Implementation overhead | Students with compiled languages
| Node.js plus Python | Fast to prototype | Can hide parallelism | Smaller async workflows
| Same language twice | Easier parity | Weak comparison | Approved explicitly
|===
