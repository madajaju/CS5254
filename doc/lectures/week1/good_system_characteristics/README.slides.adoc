== Introduction

* Course: CS 5254b - Object-Oriented Systems Under Concurrency
* Duration: 15 minutes
* Prerequisites: Basic domain modeling, object-oriented responsibilities

== Learning Objectives

* Evaluate project domain concurrency pressure
* Compare domains by shared state and workflow
* Design an adaptable object model
* Justify domain size and complexity
* Defend suitability with invariants and failure scenarios

== Opening Narrative

* Student proposes:
** Note-taking app (too simple)
** Full distributed database (too large)
* Key question: What system is small yet rich enough to fail meaningfully?

== Shared Mutable State

* Definition: Data accessed by multiple actors
* Importance: Enables concurrency failures
* Mechanisms: Workers, users, queues interact
* Failure modes: Lost updates, inconsistent reads
* Implication: Choose domains with worthwhile state

== Multi-Step Workflow

* Definition: Ordered stages in a process
* Importance: Creates invariants and coordination
* Mechanism: Ensure prerequisite completion
* Failure modes: Premature publishing or shipping
* Implication: Meaningful state transitions

== Natural Failure Potential

* Definition: Domain plausibly breaks under concurrency
* Importance: Assignments need observable failures
* Mechanism: Actors compete for resources
* Failure modes: Trivial domains lack meaningful breaks
* Implication: Select domains with realistic pressure points

== Bounded Complexity

* Definition: Complex enough for tradeoffs
* Importance: Students need to iterate designs
* Mechanism: Focused workflows with depth
* Failure modes: Overly broad systems yield vague designs
* Implication: Prefer strong workflows over weak features

== Worked Example: Podcast Production

* Problem setup:
** Episode relies on audio, transcript, artwork, review
** Publish depends on all assets

== Naive Mental Model

[source,python]
----
episode.audio_ready = True
episode.transcript_ready = True
episode.art_ready = True
episode.status = "PUBLISHED"
----

== Failure Scenario

* Condition: Publish checks state while asset updates occur
* Issues:
** Early field write may mislead readiness
** Publication could trigger twice

== Improved Design Direction

* Define central invariant:
** An episode cannot publish until all assets are complete
* Safer design: State to protect and transitions to validate

== Failure Modes and Anti-Patterns

== Symptom: Project is mostly CRUD

* Why: Domain lacks meaningful workflow
* Detect: No contested transitions
* Correct: Add shared state workflow

== Symptom: Project is too ambitious

* Why: Industry-scale system chosen
* Detect: Cannot explain in few core objects
* Correct: Narrow to one workflow

== Symptom: Failures are artificial

* Why: Lacks concurrent actors
* Detect: Unrealistic test behavior required
* Correct: Choose domains with real competition

== Symptom: Domain cannot evolve

* Why: Initial system lacks room for growth
* Detect: A1 exhausts the domain
* Correct: Select a workflow with growth potential

== Trade-Off Analysis

[cols="1,1,1,1", options="header"]
|===
| Approach | Strengths | Weaknesses | When to Use
| Podcast production | Clear workflow | Asset modeling required | Strong default
| Order fulfillment | Familiar invariants | External payment complexity | Inventory examples
| Distributed job processing | Natural concurrency | Queue infrastructure heavy | Coordinator focus
| Reservation system | Resource failure modes | Edge cases multiply | Capacity examples
| AI content pipeline | Relevant to AI | Focus on behavior vs correctness | Content workflow
|===
