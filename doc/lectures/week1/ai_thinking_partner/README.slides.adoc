== Key Concept: AI as Draft

* AI output = proposed artifact
* Must be checked before use
* Risk of false confidence
* Need for verification workflow

== Productive AI Use

* Expanding options in design
* Asking for alternatives and critiques
* Avoiding AI as an answer machine
* Prompts should focus on risks and validation

== AI Failure Modes

* Incorrect, incomplete, or misleading outputs
* Need to deliberate on predictable failures
* Examples: hallucinations, state assumptions

== Concurrency Blind Spot

* AI assumes single-threaded operations
* Focus on systems with overlapping execution
* Issues: race conditions, lost updates
* Review for shared state and interleavings

== Individual Integrity Packet

* Record of AI usage and corrections
* Distinguishes learning from outsourcing
* Contents: prompts, critiques, evidence
* Must be visible and connected to design

== Worked Example

* Problem: Publish function for an episode
* Naive implementation may pass tests
* Hidden assumption: no concurrent modifications

== Failure Scenario

* Two workers publish the same episode
* Both notify subscribers simultaneously
* AI did not handle state transitions correctly

== Safer Design Direction

* A design that ties side effects to state transitions
* Only the operation that wins the transition emits effects

```python
def publish_episode(episode_id, expected_version):
    changed = transition_status(
        episode_id,
        from_status="draft",
        to_status="published",
        expected_version=expected_version
    )
    if changed:
        notify_subscribers_once(episode_id)
```

== Integrity Packet Entry

* AI Output Summary: Simple check-then-save publish function
* Critique: Did not discuss concurrency or notifications
* Evidence: Test with multiple workers caused duplicates
* Revision: Use atomic transition and ensure idempotent notification
* Validation: Verified single publish transition per episode

== Failure Modes and Anti-Patterns

* AI produces code that compiles but violates invariants
* Invented APIs or citations
* Omissions of failure behavior
* Student inability to explain AI output
* Logged suggestions without critique

== Trade-Off Analysis

== Trade-Off Analysis

[cols="1,1,1,1", options="header"]
|===
| Approach | Strengths | Weaknesses | When to Use

| AI for brainstorming
| Expands options quickly
| Generic alternatives
| Early design exploration

| AI for code draft
| Speeds implementation
| Misses constraints
| Reviewed code units

| AI for test ideas
| Surfaces edge cases
| May lack relevance
| Validation planning

| AI for critique
| Challenges assumptions
| Misses domain-specific failures
| After baseline design

| No AI use
| Forces independent thought
| Reduces design exposure
| When unaided work is needed
|===
