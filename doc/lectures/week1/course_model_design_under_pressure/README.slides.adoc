== Opening Narrative

- Team builds a podcast service
- `Episode` object: passes tests but fails under pressure
- Focus: When does a clean model become unsafe?

== The Happy Path Trap

- Definition: Error in sequential execution path
- Issues:
  * Models seem correct
  * Assumptions on order & exclusivity
- Failure: Operations interleave and both succeed
- Implication: Evaluate states under concurrency.

== Concurrency Pressure

- Definition: Overlapping operations on shared state
- Issues:
  * Weak or optimistic object boundaries
- Failure: Duplicate processing, inconsistent updates
- Implication: Design must consider concurrency.

== Iterative Resilience

- Definition: Design, break, explain, redesign
- Issues:
  * Defending changes with evidence
- Failure: Symptoms fix, not the invariant
- Implication: Redesign follows observed failure.

== Evidence-Based Redesign

- Definition: Revision justified by concrete evidence
- Importance: Defensible claims required
- Failure: "It seems fixed" lacks validation
- Implication: Compare before and after changes.

== Worked Example Overview

- Domain: Podcast with `Episode` object
- Status transitions:
  * DRAFT
  * ASSETS_READY
  * READY_TO_PUBLISH
  * PUBLISHED

== Failure Scenario

- Issue: Two workers call `publish` simultaneously
- Results: Duplicate notifications from incorrect state handling

== Improved Design Direction

- Identify invariant: Publish once, notify once
- Safer method:
```python
def publish(episode_id, expected_version):
    updated = compare_and_set_status(
        episode_id,
        from_status="READY_TO_PUBLISH",
        to_status="PUBLISHED",
        expected_version=expected_version
    )
    if updated:
        notify_subscribers(episode_id)
```
- Focus on concurrency-aware transitions.

== Failure Modes

- Symptom: System passes sequential tests
  * Detection: Repeated concurrent tests
  * Correction: Identify shared state access
- Symptom: Duplicate notifications
  * Detection: Count side effects
  * Correction: Use idempotency keys
- Symptom: Unjustified locks
  * Detection: No clear invariant stated
  * Correction: State invariant before coordination strategy.

== Trade-Off Analysis

[cols="1,1,1,1", options="header"]
|===
| Approach | Strengths | Weaknesses | When to Use
| Sequential baseline | Simple | Hides concurrency assumptions | First pass in A1
| Coarse locking | Quick protection | May reduce throughput | Small critical sections
| Atomic state transition | Ties correctness to transition | Needs storage support | Status changes
| Single owner/coordinator | Clarifies responsibility | Can become bottleneck | Strong ordering workflows
| Idempotent operation | Handles retries | Requires careful design | Queues, retries
|===
