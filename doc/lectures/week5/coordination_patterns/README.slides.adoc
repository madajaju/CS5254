== Coordination Boundary

* Definition: Where objects agree on ordering or progress
* Importance: Must be explicit before trust under pressure
* Mechanism: State, timing, worker behavior
* Failure Mode: Duplicate work, stale state, blocked progress
* Design Implication: Expose invariant, log transitions

== Naive Implementation

* Actor performs operations
* System reads current state
* System applies transition
* System emits side effect

== Failure Scenario

* Overlapping execution can yield stale state or executed twice
* Mismatch between design assumption and execution model

== Improved Design Direction

* Name the invariant, make transitions observable
* Introduce controls: 
** Version checks
** Idempotency keys
** State-machine guards
** Explicit coordination
** Backoff retries

== Why Improved Design Is Safer

* Shifts from hoping order executes
* Proves that invalid interleavings are contained

== Failure Modes and Anti-Patterns

* Single happy-path demonstration passes
** Why: Test avoids timing or pressure conditions
** Detect: Repeat runs or stress conditions
** Correct: Add failure-focused tests

* Tool focus over design property
** Why: Focus on mechanisms before invariants
** Detect: Ask invariant protection
** Correct: State invariant first, choose mechanism

* Evidence lacks detail
** Why: Logs lack IDs or transitions
** Detect: Reviewer cannot reconstruct failure
** Correct: Capture structured evidence

* Fix changes behavior not compared to baseline
** Why: Failure was non-repeatable
** Detect: Run with same workload
** Correct: Maintain failing test for redesign

== Trade-Off Analysis

[cols="1,1,1,1", options="header"]
|===
| Approach | Strengths | Weaknesses | When to Use
| Simple baseline | Easy to implement | Hides timing assumptions | First implementation
| Guarded transition | Protects invariant | Needs careful modeling | Status changes, workflows
| Explicit coordination | Makes dependencies visible | Risk of deadlock | Multi-object workflows
| Retry-safe design | Handles duplicates | Needs deduplication | Queues, external calls
| Observability design | Produces strong evidence | Adds instrumentation | Assignments requiring proof
|===

== Practical Application

* Identify relevant invariant or progress property
* Write sequential scenario expected to succeed
* Write pressure scenario to expose failure
* Add IDs to logs before running pressure scenario
* Capture evidence before/after fix
* Update Integrity Packet: assumption, evidence
