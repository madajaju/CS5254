= Coordination Patterns

== Course Context

* Course: CS 5254b Object-Oriented Systems Under Concurrency
* Lecture: Coordination Patterns
* Prerequisites: object state, concurrency pressure, structured evidence

== Learning Objectives

* Analyze coordination pressure in a stateful concurrent system.
* Diagnose hidden assumptions behind a correct-looking baseline.
* Evaluate failure evidence from logs, traces, interleavings, or tests.
* Design a control that preserves the relevant invariant.
* Defend the approach in the Integrity Packet.

== Opening Narrative

* Two components wait for each other to make progress.
* Logs show activity, but the workflow never completes.
* Each method looks locally reasonable.
* The coordination contract is incomplete.
* The design question is: what rule makes progress observable?

== Coordination Boundary

* A coordination boundary is where independent objects must agree.
* The agreement may involve ordering, ownership, visibility, or progress.
* The boundary is often invisible in sequential code.
* Under concurrency, the boundary becomes a design obligation.
* Name the invariant before choosing the mechanism.

== Progress Guarantee

* A progress guarantee says work eventually completes.
* It prevents workflows from waiting forever without explanation.
* It must be observable in state, logs, or test output.
* Timeouts, retries, guards, and compensation may support progress.
* The guarantee must include its trade-off.

== Contention

* Contention is competition for a shared object, lock, resource, or signal.
* Contention changes timing without changing source code.
* A passing happy path may hide contention failure.
* The failure may appear as duplicate work, stale state, or blocked progress.
* Evidence must show the pressure condition.

== Hidden Assumptions

* The operation happens once.
* The operation happens in request order.
* The object state is current when read.
* A callback means the whole workflow is ready.
* A log line means the transition is safe.
* A single successful run proves correctness.

== Evidence to Collect

* Use correlation IDs for each order and operation.
* Log state before and after each transition.
* Capture wait relationships when locks or resources are involved.
* Preserve the failing workload as a repeatable test.
* Compare before and after behavior using the same scenario.
* Link evidence directly to the invariant.

== Design Response

* State the protected property first.
* Put the guard close to the transition that can violate it.
* Use ordered acquisition when multiple locks are unavoidable.
* Add timeout and compensation when waiting can become indefinite.
* Make duplicate work safe with idempotency or deduplication.
* Record the trade-off in the Integrity Packet.

== Trade-Off Analysis

[.stretch]
[cols="1,1,1,1", options="header", width="100%"]
|===
|Approach |Strengths |Weaknesses |When to Use

|Simple baseline
|Easy to explain
|Hides pressure assumptions
|Initial comparison point

|Guarded transition
|Protects the invariant directly
|Requires state modeling
|Workflow status changes

|Explicit coordination
|Makes dependencies visible
|Can create bottlenecks
|Multi-object ordering

|Retry-safe design
|Handles duplicate delivery
|Requires deduplication
|Queues and external calls

|Observability-first
|Supports review evidence
|Adds instrumentation work
|A2 design defense
|===

== Repeatable Pressure Test

[source,text]
----
scenario: order-42 coordination pressure
given: inventory callback delay is 500 ms
and: payment callback delay is 10 ms
and: two workers process the same order
when: both workers run the shipping transition
then: order state must become SHIPPED once
and: logs must show reservation confirmed before shipment
and: duplicate shipment attempts must be rejected
----

== Summary

* Coordination patterns expose where objects must agree.
* Happy-path execution can hide ordering and progress assumptions.
* The key question is which invariant must remain true under pressure.
* A mature design rejects, contains, or recovers from invalid interleavings.
* A defensible answer connects mechanism, evidence, trade-off, and risk.
