== Naive Implementation
* Assumes operations happen once in order
* Often hidden in code due to naming and passing tests
```text
actor performs operation
system reads current state
system applies transition
system emits side effect
```

== Failure Scenario
* Overlapping execution can:
  * Observe stale state
  * Execute twice
  * Arrive late
  * Leave workflow stuck
* Failure: mismatch between design assumptions and execution model

== Improved Design Direction
* Name the invariant
* Make transitions observable
* Add correctness control:
  * Version checks
  * Idempotency keys
  * Explicit coordination
  * State-machine guards
  * Retries with backoff

== Why Improved is Safer
* Shifts focus from hope to proof
* Contains/rejects invalid interleavings
* Provides evidence for recovery

== Failure Modes and Anti-Patterns
* Symptom: Happy-path passes
  * Cause: Timing/order ignored
  * Detect: Run concurrent actors/structured logs
  * Correct: Fail-focused tests on invariants

* Symptom: Tool names without design properties
  * Cause: Focus on frameworks, not what must remain true
  * Detect: Ask about invariant
  * Correct: Write invariant first

== Trade-Off Analysis
[cols="1,1,1,1", options="header"]
|===
| Approach | Strengths | Weaknesses | When to Use
| Simple baseline | Easy to explain | Hides timing assumptions | Initial comparison
| Guarded transition | Protects invariant | Needs careful modeling | Status changes
| Explicit coordination | Visible dependencies | Can cause deadlocks | Multi-object workflows
| Idempotent design | Handles duplicates | Requires control | Async workers
| Observability-first | Strong evidence | Needs instrumentation | Failure proof proof
|===
