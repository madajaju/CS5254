= Workflow Design Example
:revealjs_theme: black
:revealjs_slideNumber: true

== Lecture Focus

* Workflow mapping makes hidden ordering assumptions visible.
* A correct demo is not the same as a correct concurrent design.
* The key question is which invariant must survive pressure.
* A2 requires evidence, not just an explanation.

== Learning Objectives

* Identify the workflow invariant.
* Expose the hidden assumption in the baseline.
* Reproduce failure under pressure.
* Choose a correction that protects the invariant.
* Defend the trade-off in the Integrity Packet.

== Hidden Assumption

* The baseline assumes workflow steps are observed in request order.
* It assumes each operation happens once.
* It assumes reads see current state.
* It assumes side effects are emitted only after valid transitions.
* Concurrency makes each assumption testable.

== Pressure Sources

* Concurrent orders compete for shared resources.
* Delayed callbacks arrive after newer state.
* Retries repeat side-effect requests.
* Workers process queues out of order.
* Partial failure hides the true workflow position.

== Trade-Offs

[.stretch]
[cols="1,1,1,1", options="header", width="100%"]
|===
|Approach |Strength |Weakness |Use

|Simple baseline
|Easy to explain
|Hides pressure
|Initial comparison

|Guarded transition
|Protects invariant
|Needs state model
|Status changes

|Explicit coordination
|Makes order visible
|Can bottleneck
|Multi-object workflows

|Retry-safe design
|Handles duplicates
|Needs keys
|Async workers

|Observability-first
|Supports review
|Adds instrumentation
|A2 evidence
|===

== Summary

* Workflow mapping is a correctness tool.
* The invariant must be explicit before pressure is introduced.
* Failure evidence should reconstruct the execution.
* A mature design can be stressed, repaired, and defended.
