== Naive Implementation

* Assumption: Operations happen once in order
* Typical flow:
  * Actor performs operation
  * System reads current state
  * System applies transition
  * System emits side effect

== Failure Scenario

* Overlapping execution causes:
  * Stale state observations
  * Duplicate execution
  * Workflow blockage
* Outcome: Mismatch between design and execution model

== Improved Design Direction

* Name the invariant
* Make transitions observable
* Apply controls:
  * Version checks
  * Idempotency keys
  * State-machine guards

== Why Improved Design is Safer

* Transitions from hope to proof
* Invalid interleavings are rejected or recovered
* Evidence captured for trust

== Failure Modes

* Happy-path passes despite design weakness
  * Detect with: concurrent runs, stress tests
* Focus on mechanism instead of invariant
  * Detect by asking about protected invariant
* Vague evidence lacks operation details
  * Detect when failure cannot be reconstructed
* Fix changes behavior without baseline comparison
  * Detect absence of before/after scenarios

== Trade-Off Analysis

[cols="1,1,1,1", options="header"]
|==
| Approach | Strengths | Weaknesses | When to Use
| Simple baseline | Easy to explain and implement | Hides assumptions | Initial implementation
| Guarded state | Protects invariant directly | Requires modeling | Status changes
| Explicit coordination | Makes dependencies visible | Introduces bottlenecks | Multi-object workflows
| Idempotent design | Handles duplicates and failures | Needs ids, deduplication | Queues, retries
| Observability design | Produces strong evidence | Adds instrumentation | Requires design defense
|==
