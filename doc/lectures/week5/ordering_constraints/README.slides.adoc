= Ordering Constraints

== Course Context

* CS 5254b: Object-Oriented Systems Under Concurrency
* Week 5 lecture: Ordering Constraints
* Duration target: 15 minutes
* Assignment alignment: A2 Integrity Packet

== Learning Objectives

* Analyze ordering pressure in a stateful concurrent system
* Diagnose hidden assumptions about time, delivery, and causality
* Evaluate evidence from logs, traces, interleavings, and tests
* Design a control that preserves the relevant invariant
* Defend the decision and trade-off in the Integrity Packet

== Opening Narrative

* A publish event arrives before the approval event it depends on
* The producer sent events in the intended order
* The service processed the first message it observed
* The hidden assumption was that delivery order equals logical order

== Hidden Assumption

* Sequential code makes ordering look obvious
* Concurrent execution makes observation order unstable
* Correctness depends on logical prerequisites, not arrival timing
* The design must state what must already be true

== Preconditions and Postconditions

* A precondition states what must exist before a stage starts
* A postcondition states what is guaranteed after a stage finishes
* These conditions turn timing assumptions into checkable design rules
* A transition without a condition is hard to defend under pressure

== Design Responses

* State-machine guards reject invalid transitions
* Ordered acquisition reduces lock-cycle risk
* Idempotency keys prevent duplicate side effects
* Timeouts and compensation preserve progress evidence

== Trade-Off Analysis

[.stretch]
[cols="1,1,1,1", options="header", width="100%"]
|===
|Approach |Strengths |Weaknesses |When to Use
|Simple baseline |Easy to explain |Hides timing assumptions |First comparison point
|Guarded state transition |Protects the invariant directly |Requires explicit state modeling |Workflow status changes
|Explicit coordination |Makes dependencies visible |Can add waiting or bottlenecks |Multi-object ordering
|Idempotent design |Handles retries and duplicates |Requires keys and deduplication |Queues and external calls
|Observability-first design |Supports review evidence |Adds instrumentation work |A2 failure defense
|===

== Evidence Checklist

* Correlation ID for each workflow instance
* Entity ID for every state transition
* Timestamped prerequisite observations
* Before and after test output
* A reviewer-readable explanation of the invariant

* State the invariant before choosing the mechanism
* Preserve the failing scenario as repeatable evidence
* Explain remaining risk in the Integrity Packet

== Interview Questions

* What invariant is most relevant here?
* What hidden assumption made the baseline appear correct?
* How would you force the failure repeatedly?
* What evidence proves the failure occurred?
* Which mechanism would you choose first?
* What trade-off does that mechanism introduce?
