== Lecture Focus

* Move from single-object reasoning to workflow reasoning
* Make coordination assumptions explicit
* Protect invariants across concurrent steps
* Use evidence to diagnose failures
* Defend the design response in A2

== Core Question

* The demo can pass while the design is unsafe
* The hidden assumption is usually about order, uniqueness, or visibility
* The workflow must expose what each step requires
* The invariant must survive concurrency, retries, and delay
* The evidence must reconstruct the critical transition

== Key Terms

* Coordination manages dependencies between objects
* Workflow is a sequence of dependent stages
* Life-cycle management tracks entity progress across components
* System invariant must hold across valid executions
* Failure mode is a repeatable invariant or progress violation

== Order Workflow Example

* A single order crosses inventory, payment, and shipping
* Each service owns only part of the truth
* The order life cycle needs explicit state
* Shipping is allowed only after prerequisites are confirmed
* The workflow must reject stale or duplicate transitions

== Invariant

* An order ships only after inventory is reserved
* An order ships only after payment is captured
* Payment capture happens exactly once
* Shipment emission happens exactly once
* Every transition is logged with the order ID

== Failure Evidence

* Use one correlation ID per workflow instance
* Log entity ID, operation ID, state, and timestamp
* Preserve the failing workload
* Compare before and after runs
* Show the exact transition that violated the invariant

== Baseline Versus Corrected

[.columns]
[.column]
* Baseline assumes ordered execution
* Baseline trusts current state
* Baseline logs vague success
[.column]
* Corrected checks prerequisites
* Corrected rejects invalid transitions
* Corrected logs evidence

== Trade-Off Analysis

[.stretch]
[cols="1,1,1,1", options="header", width="100%"]
|===
|Approach |Strength |Weakness |Use

|Simple baseline
|Easy to explain
|Hides timing assumptions
|Initial comparison

|Guarded transition
|Protects invariant directly
|Requires state modeling
|Workflow status changes

|Explicit coordination
|Makes dependencies visible
|Can bottleneck or deadlock
|Multi-object ordering

|Retry-safe design
|Handles duplicates
|Needs deduplication keys
|Queues and external calls
|===

== Interview Questions

* What invariant matters most in your workflow?
* Which assumption makes the baseline appear correct?
* How can you force the failure repeatedly?
* What evidence proves the failure occurred?
* What trade-off does your fix introduce?

== Summary

* Objects hide local state changes
* Workflows expose cross-object dependencies
* Concurrency turns assumptions into failure modes
* Correct designs guard critical transitions
* Mature designs are explained, stressed, repaired, and validated
