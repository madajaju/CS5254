== Idempotent Operation

* Definition: No additional effect when called multiple times with same parameters
* Importance: Key for trusting systems under pressure
* Mechanism: Through state, timing, worker behavior
* Failure: Causes duplicate work, stale state
* Design: Expose invariant, log transitions, validate with tests

== Failure Scenario

Under delays, retries, or failures, operations can observe stale state or execute twice. This reveals a design mismatch.

== Improved Design Direction

* Name the invariant
* Make transitions observable
* Implement correctness controls: version checks, idempotency keys

== Why Improved Design Is Safer

It ensures invalid interleavings are rejected or recovered with evidence.

== Failure Modes and Anti-Patterns

* Symptom: Single happy-path test passes
  * Detection: Use repeated runs, concurrent actors
  * Correction: Add targeted failure tests

* Symptom: Names a tool, not a design property
  * Detection: Ask for the invariant
  * Correction: Write invariant first

== Trade-Off Analysis

[cols="1,1,1,1", options="header"]
|===
| Approach | Strengths | Weaknesses | When to Use
| Simple baseline | Easy to explain | Hides timing assumptions | First implementation
| Guarded state | Protects invariant | Requires state modeling | Status changes
| Explicit coordination | Dependencies visible | May introduce deadlocks | Multi-object workflows
| Idempotent design | Handles duplicates | Requires keys | Queues, retries
| Observability-first | Strong evidence | Adds instrumentation | Failure proofing
|===
