== Core Concepts

== Sequence Numbers / Versioning

* Definition: Monotonically increasing number for events
* Importance: Explicit identification of conditions needed
* Mechanism: Through state, timing, retries, etc.
* Failure Mode: Duplicate work, stale state, misleading evidence
* Design Implication: Log transitions, validate with tests


== Causal Ordering

* Definition: Event B cannot process before Event A
* Importance: Necessary condition for trustworthiness
* Mechanism: Appears through state, timing, etc.
* Failure Mode: Duplicate work, blocked progress
* Design Implication: Log transitions, validate with tests


== Buffering/Reordering

* Definition: Temporary buffer for early events
* Importance: Explicit conditions are vital
* Mechanism: Through state, timing, retries, etc.
* Failure Mode: Duplicate work, stale state, misleading evidence
* Design Implication: Log transitions, validate with tests


== Partitioning / Sharding

* Definition: Events for the same entity handled together
* Importance: Critical for maintaining order
* Mechanism: Through state, timing, retries, etc.
* Failure Mode: Duplicate work, stale state, blocked progress
* Design Implication: Log transitions, validate with tests


== Asynchronous Boundary

* Definition: Work continues later, on another worker
* Importance: Must be made explicit for trust
* Mechanism: Through state, timing, retries, etc.
* Failure Mode: Duplicate work, stale state, misleading evidence
* Design Implication: Log transitions, validate with tests

== Naive Implementation

* Assumes operation occurs in order
* Often invisible in code

```
actor performs operation
system reads current state
system applies transition
system emits side effect
```

== Failure Scenario

* Overlapping execution, delay, retry, or partial failure
* Operations can observe stale state or execute twice


== Improved Design Direction

* Name invariant, make transitions observable
* Add correctness controls: version checks, idempotency

== Why Improved Design Is Safer

* Shifts focus to proving invariants
* Rejects, contains, or recovers invalid interleavings


== Failure Modes and Anti-Patterns

* Symptom: System passes single happy-path test
  * Why: Test avoids revealing design weaknesses
  * Detection: Use concurrent actors, stress tests
  * Correction: Add failure-focused tests for invariants

* Symptom: Names a tool, not a design property
  * Why: Focus on mechanics over invariants
  * Detection: Ask for the invariant protection
  * Correction: State invariant first, then mechanism

* Symptom: Vague evidence for claims
  * Why: Logs lack details for reconstruction
  * Detection: Reviewer can’t verify failure
  * Correction: Capture structured evidence

* Symptom: Fix changes behavior but not compared
  * Why: Failure not preserved repeatably
  * Detection: No before/after comparison
  * Correction: Preserve and rerun failing test


== Trade-Off Analysis

[cols="1,1,1,1", options="header"]
|===
| Approach | Strengths | Weaknesses | When to Use
| Simple baseline | Easy to explain | Hides timing assumptions | Initial implementation comparison
| Guarded state transition | Protects core invariant | Requires careful modeling | Status changes, workflows
| Explicit coordination | Makes dependencies visible | May cause deadlocks | Multi-object workflows
| Idempotent design | Handles duplicates | Needs deduplication | Queues, retries, async
| Observability-first | Strong evidence | Needs instrumentation | Assignments needing proof
|===
