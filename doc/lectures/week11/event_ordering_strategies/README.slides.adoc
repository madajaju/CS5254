= Event Ordering Strategies

== Opening Narrative
[.column]
* A publish event can arrive before the approval event it depends on.
* The service may process the first message it sees and corrupt the workflow.
* Hidden assumption: delivery order equals logical order.

[.column]
* The design question is how the system should reason when time and causality diverge.
* The pressure is not syntax; it is execution order under concurrency and retries.

== Trade-Offs
[.stretch]
[cols="1,1,1,1", options="header", width="100%"]
|===
|Approach
|Strengths
|Weaknesses
|When to use

|Simple baseline
|Easy to explain and implement
|Hides timing assumptions
|First pass and comparison point

|Guarded transition
|Protects the invariant directly
|Requires careful state modeling
|Workflow steps and status changes

|Explicit coordination
|Makes dependencies visible
|Can add waiting or bottlenecks
|Multi-object ordering requirements

|Idempotent design
|Handles duplicates and retries
|Needs keys and deduplication
|Queues and async workers
|===

== Practical Application
* Identify the invariant or progress property.
* Write one sequential scenario that should succeed.
* Write one pressure scenario that could fail.
* Add operation IDs and entity IDs to logs.
* Capture before and after evidence if you apply a fix.
* Update the Integrity Packet with assumption, evidence, validation, and remaining risk.
