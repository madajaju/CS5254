== Worked Example: Problem Setup

* Podcast Domain: Log aggregator shows `Episode-123` picked by `Worker-A`.
* Trace Analysis: `Publish` event processed before `Cleaned` event.

== Naive Implementation

* Assumes operation happens once, in order, with current state.
* Illustration:
    actor performs operation
    system reads current state
    system applies transition
    system emits side effect

== Failure Scenario

* Under overlapping execution, the same operation can:
  * observe stale state
  * execute twice
  * arrive late
  * leave the workflow stuck

== Improved Design Direction

* Name the invariant and make transitions observable.
* Add correctness controls appropriate to failure:
    * version checks
    * idempotency keys
    * explicit coordination

== Why the Design Is Safer

* Shift from hoping the workflow executes correctly to proving it.

== Failure Modes and Anti-Patterns

* **Symptom**: System passes happy-path test.
    * **Detection**: Add concurrent actors or stress conditions.
    * **Correction**: Preserve happy-path but add failure-focused tests.
* **Symptom**: Naming tools, not design properties.
    * **Detection**: Ask which invariant the mechanism protects.
* **Symptom**: Vague evidence.
    * **Detection**: Logs lack IDs/timing.
    * **Correction**: Capture structured evidence.

== Trade-Off Analysis

[cols="1,1,1,1", options="header"]
|===
| Approach | Strengths | Weaknesses | When to Use
| Simple baseline | Easy to explain | Hides timing assumptions | Initial implementation
| Guarded transition | Protects core invariant | Requires careful modeling | Workflow changes
| Explicit coordination | Visible dependencies | Can cause deadlocks | Multi-object workflows
| Idempotent design | Handles duplicates | Requires deduplication | Queues, async workers
| Observability-first | Strong evidence | Adds instrumentation | Failure proof assignments
|===
