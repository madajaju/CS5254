== Throughput (TPS/RPS)

* Definition: transactions per second
* Importance: must be explicit under pressure
* Failure mode: can obscure duplicate work
* Design: expose invariant, log transitions

== Latency (p95/p99)

* Definition: time for 95% requests to complete
* Importance: explicit condition for trust
* Failure mode: can obscure system behavior
* Design: log critical transitions, validate behavior

== Ramp-up

* Definition: gradual load increase
* Importance: identify degradation points
* Failure mode: can hide failures
* Design: log transitions, validate with tests

== Steady State

* Definition: consistent load over time
* Importance: detect leaks, exhaustion
* Failure mode: hidden problems could arise
* Design: log transitions, validate behavior

== Operational Pressure

* Definition: stress conditions revealing limits
* Importance: explicit conditions for trust
* Failure mode: can miss system weaknesses
* Design: log behavior under various conditions

== Naive Implementation

* Assumes order and current state
* Invisible assumption in code
* *Actor performs operation* 
* *System reads current state*

== Failure Scenario

* Overlapping execution, stale state
* Late deliveries or retries introduce issues
* Evidence of design assumption mismatch

== Improved Design Direction

* Name the invariant, make transitions observable
* Use version checks, idempotency, coordination
* Ensure invalid instances are prevented

== Safety of Improved Design

* Moves from hoping to proving workflow order
* Rejects invalid interleavings with evidence
* Strengthens confidence in system behavior

== Failure Modes and Anti-Patterns

* Symptom: passes happy path only
  * Detection: add concurrent runs
* Symptom: vague evidence
  * Detection: lack of operation IDs
* Symptom: fixes not compared to baseline
  * Detection: no before/after run

== Trade-Off Analysis

[cols="1,1,1,1", options="header"]
|===
| Approach | Strengths | Weaknesses | When to Use
| Simple baseline | Easy to implement | Hides pressure assumptions | First comparison point
| Guarded state | Protects core invariant | Requires modeling | Status changes, reservations
| Explicit coordination | Visible dependencies | May introduce bottlenecks | Multi-object workflows
| Idempotent design | Handles duplicates | Requires deduplication | Queues, async workers
| Observability-first | Strong evidence | Adds instrumentation | When failure proof needed
|===
