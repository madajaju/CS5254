= What is System Stress?

== Stress as Design Pressure
* Stress is pressure that reveals whether a system still behaves correctly.
* It appears as load, timing shifts, retries, queues, or contention.
* The key question is whether the invariant still holds under pressure.
* A good design makes stress observable and testable.

== Stress and Hidden Assumptions
[.column]
Assumptions
* The workflow runs once
* State changes happen in order
* Load does not change behavior
* Failure evidence is optional

[.column]
Reality
* Concurrent runs overlap
* Timing affects state visibility
* Pressure exposes limits
* Evidence is required to defend the design

== Failure Under Pressure
* One sequential run can hide the real execution model.
* Hidden assumptions make code look correct before pressure is introduced.
* Under load, the same workflow may interleave, delay, or repeat.
* The failure is often in the design assumption, not the syntax.
* Repeatable pressure tests expose the gap between intent and reality.

== Failure Scenario
[.column]
Symptoms
* Latency spikes
* Duplicate work
* Missing completion logs
* Unbounded queue growth

[.column]
Causes
* Slow dependencies
* Retry storms
* Stale state
* Hidden coordination costs

== Evidence Under Pressure
* Stress must be supported by structured evidence.
* Useful evidence includes logs, traces, interleavings, and repeatable test output.
* Evidence should show baseline behavior and failure behavior.
* Evidence should also show the correction and its trade-off.
* Without evidence, the claim is hard to defend in review.

== Design Responses to Stress
* Protect the invariant directly with state guards or version checks.
* Limit damage with backpressure, retries, or circuit breakers.
* Make duplicate work safe with idempotency or deduplication.
* Recover with compensation or reconciliation when needed.
* Choose the smallest control that preserves the relevant property.

== Repair Strategy
[.column]
Before
* Hope the happy path represents reality
* Treat logs as optional
* Accept hidden timing assumptions

[.column]
After
* Name the invariant
* Add structured evidence
* Apply backpressure, guards, or idempotency

== Stress Concepts
[.stretch]
[cols="1,1,1,1", options="header", width="100%"]
|===
| Concept | What it Means | Typical Failure | Design Response

| Stress
| Pressure that exposes limits
| A passing design starts failing under load
| Measure, log, and test the invariant

| Contention
| Multiple actors fight for the same resource
| Blocked progress or duplicate work
| Reduce shared access or coordinate explicitly

| Saturation
| More work reduces performance
| Queue growth and timeouts
| Add backpressure or bounded capacity

| Edge Cases
| Rare timing combinations under load
| Intermittent and hard-to-repeat failures
| Use repeated runs and structured evidence
|===
