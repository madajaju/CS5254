== Introduction

* System passes functional tests.
* Under load, issues emerge.
* Key question: How does pressure reveal system behavior?

== Learning Objectives

* Analyze system stress in concurrent systems.
* Diagnose hidden assumptions.
* Evaluate failure evidence.
* Design controls preserving invariants.
* Defend approach using Integrity Packet.

== Core Concept: Stress

* Definition: Pushing system operational limits.
* Importance: Trust under pressure requires explicit definition.
* Mechanism: Object state, timing, worker behavior.
* Failure Mode: Can create duplicates, blocked progress.
* Design Implication: Expose invariants and validate with tests.

== Core Concept: Contention

* Definition: Multiple threads vie for the same resource.
* Importance: Requires explicit identification for trust under pressure.
* Mechanism: Observed through object state and timing.
* Failure Mode: Duplicates and stale states if ignored.
* Design Implication: Expose invariants; ensure validation.

== Core Concept: Saturation

* Definition: Adding work reduces performance.
* Importance: Trust requires awareness of system limits.
* Mechanism: Timing and state issues under load.
* Failure Mode: Duplicates and staleness if not tracked.
* Design Implication: Focus on observable transitions.

== Core Concept: Edge Cases

* Definition: Rare timing combinations under heavy load.
* Importance: Must be made explicit to trust the system.
* Mechanism: Workflow and state behavior must be monitored.
* Failure Mode: Can lead to duplicates and blocked workflows.
* Design Implication: Highlight invariants; validate behavior.

== Core Concept: Operational Pressure

* Definition: Conditions revealing hidden limits.
* Importance: Trust requires identification of system pressures.
* Mechanism: State and behavior affected by load.
* Failure Mode: Can create misleading evidence.
* Design Implication: Expose and log key transitions.

== Worked Example: Podcast Domain

* Stress: Processing 50 episodes, each with 5 assets.
* Result: In-memory data grows, CPU usage peaks.

== Naive Design Assumption

* Assumes operation occurs once and in order.
* Invisible failures in code due to misleading method names.

```text
actor performs operation
system reads current state
system applies transition
system emits side effect
```

== Failure Scenario

* Overlapping execution can observe stale state.
* Issues arise from mismatched design assumptions.

== Improved Design Direction

* Name invariants and make transitions observable.
* Implement version checks, idempotency, and controls.

== Safer Design Rationale

* Moves from assumption to proof against interleaving issues.
* Strengthens error containment and recovery mechanisms.

== Failure Modes

* Symptom: Passes single happy-path test.
  * Detection: Use concurrent actors or stress tests.
  * Correction: Add targeted failure tests.

* Symptom: Names a tool, not a design property.
  * Detection: Identify protected invariants.
  * Correction: Define invariants before choosing mechanisms.

== Trade-Off Analysis

[cols="1,1,1,1", options="header"]
|===
| Approach | Strengths | Weaknesses | When to Use
| Simple baseline | Easy implementation | Hides timing assumptions | First comparison
| Guarded state transition | Protects invariants | Requires careful modeling | Core workflows
| Explicit coordination | Visible dependencies | May introduce issues | Multi-object coordination
| Idempotent design | Handles duplicates | Needs deduplication | Async workflows
| Observability-first | Strong evidence | Adds instrumentation | Formal reviews
|===
