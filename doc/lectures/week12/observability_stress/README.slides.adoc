== Improved Design Direction

* Name invariants clearly
* Make transitions observable
* Control correctness: version checks, retries, coordination

== Why Improved Design Is Safer

* Moves from hoping order to proving invariants
* Rejects invalid interleavings with evidence

== Failure Modes

* System passes single happy-path test
  * Detection: Add concurrent runs, structured logs
  * Correction: Include failure-focused tests

* Uses tool names, not design property
  * Detection: Ask invariant the mechanism protects
  * Correction: Write invariant first

* Evidence is vague
  * Detection: Reviewers can't reconstruct failure
  * Correction: Capture structured evidence

* Fix changes behavior with no baseline
  * Detection: No repeatable scenarios
  * Correction: Keep failing tests for comparison

== Trade-Off Analysis

[cols="1,1,1,1", options="header"]
|===
| Approach | Strengths | Weaknesses | When to Use
| Simple baseline | Easy to explain | Hides timing assumptions | First implementation
| Guarded state transition | Protects core invariant | Careful modeling required | Status changes
| Explicit coordination | Shows dependencies | Can cause deadlock | Multi-object workflows
| Idempotent design | Handles duplicates | Requires control keys | Queues, retries
| Observability-first | Strong evidence | Adds instrumentation | Failure proof assignments
|===
