* Key inquiry: What must engineers analyze before trusting results under pressure?

== Retry Storms

* Definition: Multiple workers retry simultaneously; can overwhelm systems.
* Impact: Must be explicit for system reliability.
* Mechanism: Related to object state, workflow timing, retries.
* Failure Mode: Risk of producing duplicates or misleading evidence.
* Design Implication: Log critical transitions and validate behavior.

== Partial Success Failure

* Definition: Worker completes partial task, then fails, causing conflicts.
* Impact: Similar importance for system reliability.
* Mechanism: Appears through state, workflow timing, retries.
* Failure Mode: Duplicate work or stale state.
* Design Implication: Maintain invariants, log transitions, validate.

== Zombie Resources

* Definition: Multiple copies of a resource due to retries.
* Impact: Implications under pressure.
* Mechanism: Object state, worker behavior, coordination.
* Failure Mode: Duplicate work or stalled workflows.
* Design Implication: Expose invariants, log transitions.

== System Invariants

* Definition: Conditions that must hold true across executions.
* Impact: Critical for trustworthy systems.
* Mechanism: Observes state, timing, coordination.
* Failure Mode: Breach leads to duplicates or inconsistencies.
* Design Implication: Structural evidence and validation.

== Worked Example: Podcast Domain

* Scenario: Uploading a 1GB file drops at 99%, retries consume 2GB bandwidth.
* Assumption: Operations succeed without error.
* Failure: System confused by retries, stale state or delays.

== Failure Scenario Overview

* Overlapping execution introduces unexpected states.
* Failure arises from design assumptions vs. reality.

== Improved Design Direction

* Principle: Name the invariant; make transitions observable.
* Controls: Version checks, idempotency keys, explicit retries.
* Shift focus from hope to proof in execution order.

== Failure Modes and Anti-Patterns

* Symptom: Single happy-path success.
** Why: Tests avoid pressure conditions.
** Detect: Concurrent tests, stress conditions.
** Correct: Add focused failure tests.

* Symptom: Tool name, not a design property.
** Why: Mechanism chosen without invariant clarity.
** Detect: Ask for the protected invariant.
** Correct: Write invariant first.

== Trade-Off Analysis

[cols="1,1,1,1", options="header"]
|===
| Approach | Strengths | Weaknesses | Use Case
| Simple baseline | Easy to explain | Hides timing assumptions | Initial comparison
| Guarded transition | Protects invariant | Requires modeling | Dynamic status changes
| Explicit coordination | Visible dependencies | Risk of bottlenecks | Complex workflows
| Idempotent design | Manages duplicates | Needs deduplication | Queues and external calls
| Observability-first | Strong evidence | Adds instrumentation | Needs design proof
|===
