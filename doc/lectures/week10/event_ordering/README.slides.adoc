== Learning Objectives

* Analyze design pressure due to out-of-order events
* Diagnose hidden assumptions in the system
* Evaluate failure evidence using logs and traces
* Design corrections to preserve invariants
* Defend approaches in the Integrity Packet

== Opening Narrative

* Arriving events might not follow expected order.
* Logic dictates that delivery order ≠ logical order.
* System must adapt when time and causality diverge.

== Core Concepts: Non-FIFO Queues

* Definition: Many queues don’t guarantee order.
* Importance: Must be explicit for system trust.

== Core Concepts: Race to the Consumer

* Definition: Event B can finish before Event A.
* Importance: Must clarify under pressure.

== Core Concepts: State Regression

* Definition: Older event overwrites newer.
* Importance: Trust requires explicit handling.

== Core Concepts: Asynchronous Boundary

* Definition: Work continues later or on different worker.
* Importance: Needs clear communication.

== Core Concepts: Temporal Coupling

* Definition: Hidden dependency on event timing.
* Importance: Must be made clear for trust.

== Worked Example

== Problem Setup

* **Podcast Domain**: `EpisodeApproved` sent, then `EpisodePublished`. 
* Fails if `Published` arrives first.

* **Order System**: `CancelOrder` arriving before `CreateOrder`.

== Naive Implementation

A naive design assumes operations happen once, in order.

[source,language]
----
actor performs operation
system reads current state
system applies transition
system emits side effect
----

== Failure Scenario

* Overlap causes stale state or late arrivals.

== Improved Design Direction

* Name invariant and make transitions observable.

== Why Improved Design Is Safer

* Proves invalid interleavings are handled effectively.

== Failure Modes: Single Happy-Path Pass

* Symptom: System passes a single happy-path demonstration.
* Why: Test misses timing pressures.

== Failure Modes: Tool vs. Property

* Symptom: Names a tool, not a design property.
* Why: Focus shifts to mechanisms over invariants.

== Failure Modes: Vague Evidence

* Symptom: Evidence is too vague to support the claim.
* Why: Insufficient logs; cannot trace failures.

== Failure Modes: Fix Without Comparison

* Symptom: Fix changes behavior without comparison.
* Why: Baseline not preserved as a scenario.

== Trade-Off Analysis

[cols="1,1,1,1", options="header"]
|===
| Approach | Strengths | Weaknesses | When to Use
| Simple baseline | Easy to explain | Hides timing assumptions | Initial implementation
| Guarded transition | Protects invariant | Needs careful modeling | Status changes
| Explicit coordination | Visibility of dependencies | May cause delays | Multi-object workflows
| Idempotent design | Handles duplicates | Needs keys & deduplication | Queues, retries
| Observability design | Strong evidence | Adds instrumentation | Assignments needing proof
|===

== Practical Application

* Identify relevant invariant for out-of-order events.
* Write a scenario expected to succeed.
* Write a pressure scenario to expose failure.
* Enhance logs with operation and entity IDs.
* Capture evidence before/after fixes.
* Update Integrity Packet with assumptions and validations.
