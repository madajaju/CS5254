== Opening Narrative

* Message delivered again; duplicate processing occurs.
* System is broken due to lack of tolerance for duplicates.
* Need to address what changes to prevent workflow corruption.

== Core Concept: At-Least-Once Delivery

* **Definition**: Message guarantee may deliver more than once.
* **Importance**: Must be explicit for system trust under pressure.
* **Mechanisms**: Object state, timing, retries, coordination.
* **Failure Mode**: Duplicate work, stale state, misleading evidence.
* **Design Implication**: Expose invariant; validate behavior.

== Core Concept: Double Processing

* **Definition**: Same task picked by two workers or a worker twice.
* **Importance**: Must be clear before trusting system under pressure.
* **Mechanisms**: Timing, state, retries, coordination.
* **Failure Mode**: Duplicate work, state corruption, misleading paths.
* **Design Implication**: Make transitions clear; validate with tests.

== Core Concept: Side Effect Inflation

* **Definition**: Negative impact of repeating work (e.g., double charges).
* **Importance**: Must be explicit to ensure system trust.
* **Mechanisms**: Object state, workflow timing, worker behavior.
* **Failure Mode**: Duplicate outputs, stale states, evidence issues.
* **Design Implication**: Expose invariants, log transitions.

== Core Concept: System Invariant

* **Definition**: Condition that holds true across executions.
* **Importance**: Must be made explicit for system reliability.
* **Mechanisms**: State, timing, retries.
* **Failure Mode**: Violation of conditions leading to errors.
* **Design Implication**: Expose invariant, validate with tests.

== Core Concept: Failure Mode

* **Definition**: Recurrent violation of invariants or progress loss.
* **Importance**: Necessitates clear system assumptions.
* **Mechanisms**: Timing, state, intersections of workflow.
* **Failure Mode**: Duplicate work and misleading process evidence.
* **Design Implication**: Document invariants, validate transitions.

== Naive Implementation

* Assumes operation occurs once and correctly.
* Invisible design assumption leads to false confidence.

```text
actor performs operation
system reads current state
system applies transition
system emits side effect
```

== Failure Scenario

* Overlap execution leads to stale state, or stuck workflow.
* Misalignment between design and execution model.

== Improved Design Direction

* Name invariant, ensure observable transitions, add controls.
* Introduce version checks, idempotency keys, or retries.

== Safer Design Rationale

* Shift from hoping for order to proving invalid states are addressed.
* Ensures that workflow interleavings are managed adequately.

== Failure Modes and Anti-Patterns

* **Symptom**: Single happy-path test passes.
  * **Detection**: Add concurrent events or structured logging.
  * **Correction**: Maintain happy-path test with failure scenarios.

* **Symptom**: Focus on tools rather than design properties.
  * **Detection**: Identify mechanism protecting invariant.
  * **Correction**: State invariant first, then select mechanism.

* **Symptom**: Vague evidence fails to support claims.
  * **Detection**: Reviewer cannot trace failures.
  * **Correction**: Capture structured evidence directly linked to claims.

* **Symptom**: Fix alters behavior with no baseline comparison.
  * **Detection**: Lacks a repeatable failure case.
  * **Correction**: Retain failing test; rerun post-redesign.

== Trade-Off Analysis

[cols="1,1,1,1", options="header"]
|===
| Approach | Strengths | Weaknesses | When to Use
| Simple baseline | Easy to explain/implement | Hides timing assumptions | First implementation
| Guarded transitions | Protects core invariant | Needs careful modeling | Workflow steps
| Explicit coordination | Displays dependencies clearly | Risk of deadlocks | Multi-object workflows
| Idempotent design | Manages duplicates | Requires additional control | Queued operations
| Observability focus | Strong evidence production | Instrumentation needed | Failure proof assignments
|===
