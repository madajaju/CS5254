== Core Concept: Mutable Shared State

* Definition: Data accessed by multiple threads.
* Importance: Must be explicit for trusted system under pressure.
* Mechanisms: 
  * Object state
  * Workflow timing
  * Worker behavior
  * Queues
  * Coordination boundaries
* Failure Mode: 
  * Duplicate work
  * Stale state
  * Blocked progress
  * Misleading evidence
* Design Implication: Expose invariant, log transition, validate behavior.

== Worked Example: Problem Setup

* **Podcast Domain**: 
  * *Unsafe*: global `static List<Episode> allEpisodes` accessed by multiple workers.
  * *Safe*: local `List<Asset> localAssets` within one worker’s execution.
* **Inventory System**: shared `Integer count` decremented by purchase threads.

== Naive Implementation

A naive design assumes:
* Operation happens once, in order, with current state.
* Assumption often invisible.
```
actor performs operation
system reads current state
system applies transition
system emits side effect
```

== Failure Scenario

* Under concurrent execution or retries:
  * Observes stale state.
  * Executes twice.
  * Workflow left stuck.
* Failure is a mismatch between assumption and execution.

== Corrected Design Direction

* Name the invariant.
* Make transitions observable.
* Add correctness controls:
  * Version checks
  * Idempotency keys
  * State-machine guards
  * Explicit coordination

== Why Is Improved Design Safer?

* Changes focus from hoping for correct execution to:
  * Proving invalid interleavings are rejected or recovered with evidence.

== Failure Modes & Anti-Patterns

* Symptom: System passes single happy-path test.
  * **Detection**: Add repeated runs, concurrent actors.
* Symptom: Tool names precede design properties.
  * **Detection**: Ask which invariant is protected.
* Symptom: Evidence is vague.
  * **Detection**: Logs lack necessary identifiers or transitions.
* Symptom: Fix changes behavior without comparison.
  * **Detection**: No before/after repeatable scenario.

== Trade-Off Analysis

[cols="1,1,1,1", options="header"]
|===
| Approach | Strengths | Weaknesses | When to Use
| Simple baseline | Easy to explain | Hides timing assumptions | Initial implementation
| Guarded transition | Protects core invariant | Requires careful modeling | Status changes
| Explicit coordination | Makes dependencies visible | May introduce deadlocks | Complex workflows
| Idempotent design | Handles duplicates | Requires side-effect control | Queues, retries
| Observability-first | Provides strong evidence | Needs instrumentation | Failure proof
|===
