* Importance: Trust only under pressure
* Mechanism: Object state, timings, worker behavior
* Failure mode: Duplicate work, stale state, misleading evidence
* Design implication: Expose invariant, log transitions

== Failure Modes and Anti-Patterns

* Symptom: System passes happy path
  * Why: test avoids timing or pressure
  * Detection: repeat runs, concurrent actors
  * Correction: add failure-focused tests

* Symptom: Explanation names tool, not property
  * Why: focus on mechanisms over invariants
  * Detection: Ask which invariant is protected
  * Correction: Write invariant first, select mechanism

* Symptom: Evidence too vague
  * Why: logs lack critical details
  * Detection: Reviewer can't reconstruct failure
  * Correction: Capture structured evidence

== Trade-Off Analysis

[.stretch]
[cols="1,1,1,1", options="header", width="100%"]
|===
| Approach | Strengths | Weaknesses | When to Use
| Baseline | Easy to build | Hides timing | First pass
| Guarded transition | Protects invariant | Needs modeling | Status changes
| Coordination | Visible dependencies | Deadlock risk | Multi-object flows
| Idempotency | Handles duplicates | Needs keys | Queues, retries
| Observability | Strong evidence | Adds logging | Proof needed
|===

== Practical Application

* Identify the invariant relevant to forcing failure
* Write sequential scenario that should succeed
* Write pressure scenario exposing failure
