== Naive Implementation

* Assumes operation happens once, in order
* Invisible in code: method name sounds correct
* Execution flow:
  * actor performs operation
  * system reads current state
  * system applies transition
  * system emits side effect

== Failure Scenario

* Under concurrency: observe stale state
* Operation can execute twice or leave workflow stuck
* Not just syntax bug: mismatch in design and execution

== Improved Design Direction

* Name invariant and make transition observable
* Add correctness controls:
  * version checks
  * idempotency keys
  * explicit coordination

== Why Improved Design Is Safer

* Changes problem: proves invalid interleavings are handled
* Reject, contain, or recover with evidence

== Failure Modes and Anti-Patterns

* Symptom: System passes happy path
  * Why: test avoids timing or pressure
  * Detection: repeat runs, concurrent actors
  * Correction: add failure-focused tests

* Symptom: Explanation names tool, not property
  * Why: focus on mechanisms over invariants
  * Detection: Ask which invariant is protected
  * Correction: Write invariant first, select mechanism

* Symptom: Evidence too vague
  * Why: logs lack critical details
  * Detection: Reviewer can't reconstruct failure
  * Correction: Capture structured evidence

== Trade-Off Analysis

[cols="1,1,1,1", options="header"]
|===
| Approach | Strengths | Weaknesses | When to Use
| Simple baseline | Easy implementation | Hides timing assumptions | First implementation
| Guarded transition | Protects invariant | Requires state modeling | Status changes
| Explicit coordination | Makes dependencies visible | Can introduce deadlocks | Multi-object workflows
| Idempotent design | Handles duplicates | Needs keys for control | Queues, retries
| Observability-first | Strong evidence | Adds instrumentation | Assignments needing proof
|===
