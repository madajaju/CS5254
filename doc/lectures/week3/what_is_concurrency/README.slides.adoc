== Core Concepts

* Interleaving
** Definition: Switching tasks on single core rapidly
** Importance: Must be explicit for trust
** Failure Mode: Duplicate work, stale state
** Design Implication: Expose invariants, log transitions

== Core Concepts (continued)

* Parallelism
** Definition: Running multiple tasks on multiple cores
** Importance: Must be explicit for trust
** Failure Mode: Duplicate work, stale state
** Design Implication: Expose invariants, log transitions

== Core Concepts (continued)

* Context Switching
** Definition: Saving and restoring thread state
** Importance: Must be explicit for trust
** Failure Mode: Duplicate work, stale state
** Design Implication: Expose invariants, log transitions

== Core Concepts (continued)

* Non-Determinism

** Design Implication: Expose invariants, log transitions

== Core Concepts (continued)

* System Invariant

== Worked Example

* Race Condition

== Naive Implementation Model

* Assumes single operation in order
* Often invisible in code
** Actor performs operation
** System reads current state
** System applies transition
** System emits side effect

== Failure Scenario

* Overlapping execution or partial failure risks
* Stale state or late arrivals can occur
* Mismatch between assumption and execution model

== Improved Design Direction

* Name invariant and ensure observable transitions
* Add controls: version checks, idempotency
* Focus on proactive orchestration and recovery

== Why Improved Design Is Safer

* Shifts focus from hope to proof
* Ensures invalid interleavings are contained or recovered

== Failure Modes

* Symptom: Passes happy-path demonstration
** Avoids conditions exposing design weakness
* Correction: Add failure-focused tests.

== Failure Modes (continued)

* Symptom: Names tool but not property
** Focus on mechanisms over invariants
* Correction: State invariant then select mechanism.

== Failure Modes (continued)

* Symptom: Vague evidence
** Logs lack structure or detail
* Correction: Link evidence to design claims.

== Trade-Off Analysis

[cols="1,1,1,1", options="header"]
|===
| Approach | Strengths | Weaknesses | When to Use
| Simple baseline | Easy to explain | Hides pressure assumptions | First implementation
| Guarded transition | Protects core invariant | Requires modeling | Status changes
| Explicit coordination | Makes dependencies clear | Can introduce bottlenecks | Multi-object workflows
| Idempotent design | Handles duplicates | Requires deduplication | Queues, retries
| Observability-first | Strong evidence | Adds instrumentation | Assignments requiring defense
|===
