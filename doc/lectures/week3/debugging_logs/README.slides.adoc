== Interleaved Log Analysis
* Definition: A method for validating concurrent behavior
* Importance: Ensures system reliability under pressure
* Mechanism: Influenced by states, timing, and coordination
* Failure Mode: Can result in duplicate work or misleading evidence
* Design Implication: Log transitions and validate tests

== System Invariant
* Definition: A condition maintaining truth across executions
* Importance: Key to trusting systems under concurrency
* Mechanism: Revealed through state, timing, and behavior
* Failure Mode: Leads to blocked progress and stale states
* Design Implication: Log transitions to validate behavior

== Failure Mode
* Definition: Repeatable system violations of invariants
* Importance: Highlights conditions for trust in the system
* Mechanism: Reveals issues through state and timing
* Failure Mode: Causes duplicate work or blocked workflows
* Design Implication: Log critical transitions for validation

== Worked Example
* Podcast Domain Log Example
** `12:00:00.001 [Thread-1] Checking status for Ep-1: DRAFT`
** `12:00:00.002 [Thread-2] Checking status for Ep-1: DRAFT`
** `12:00:00.005 [Thread-1] Updating status to PROCESSING`
** `12:00:00.006 [Thread-2] Updating status to PROCESSING`
* Analysis: Validates read before update conflict

== Naive Implementation
* Assumption: Operation occurs once, in order
* Execution model: Hidden in method behavior
```text
actor performs operation
system reads current state
system applies transition
system emits side effect
```

== Failure Scenario
* Overlapping execution leads to:
** Stale state observation
** Duplicate execution of updates
** Workflow becoming stuck
* Not just a syntax bug; breaks the design assumption

== Corrected Design Direction
* Name the invariant and make transitions observable
* Controls for correctness: Version checks, idempotency, coordination, retries

== Why Safer Design?
* Moves from assumption of execution order to proof of valid interleavings
* Ensures invalid scenarios are rejected or recoverable

== Failure Modes
* Symptom: Single happy-path demonstration passes
** Test does not simulate real pressure or timing
** Detection: Use concurrent actors and structured logs
* Symptom: Focus on tools, not design properties
** Detection: Identify which invariant is being protected
* Symptom: Vague evidence fails to support claims
** Detection: Logs need operation IDs and timestamps

== Trade-Off Analysis
[cols="1,1,1,1", options="header"]
|===
| Approach | Strengths | Weaknesses | When to Use
| Simple baseline | Easy to explain | Hides timing assumptions | First implementation
| Guarded state transition | Protects invariants | Careful state modeling needed | Status changes
| Explicit coordination | Visible dependencies | Risk of deadlock | Multi-object workflows
| Idempotent design | Handles duplicates | Requires deduplication | Queues and retries
| Observability-first | Strong review evidence | Adds instrumentation | Failure proof requirements
|===
