== Core Concept: Deadlock

* Definition: Waiting threads block each other
* Importance: Must be explicit for trust
* Mechanism: Appears via state, timing, behavior
* Failure: Passes happy path, causes duplicates, stalling
* Design: Expose invariant, log transitions, validate

== The Four Conditions

* Mutual Exclusion
* Hold and Wait
* No Preemption
* Circular Wait

== Failure Scenario: Circular Wait

* Thread A: holds Resource 1, waits for Resource 2
* Thread B: holds Resource 2, waits for Resource 1
* Design implication: Expose invariant

== Coordination Boundary

* Definition: Agreement on ordering/ownership
* Importance: Ensures system trust under pressure
* Design: Validate behavior with tests, log transitions

== Progress Guarantee

* Definition: Work completes instead of waiting indefinitely
* Importance: Identifies trust condition
* Design implication: Expose invariant, validate behavior

== Naive Implementation

* Assumes single execution in order
* Invisible assumptions in code
* Example Transition Flow:
  * Actor performs operation
  * System reads state
  * System applies transition
  * System emits side effect

== Failure Scenario

* Overlapping execution causes:
  * Stale state
  * Duplicate execution
  * Workflow stuck
* Mismatch between design and execution model

== Corrected Design Direction

* Name the invariant
* Make transitions observable
* Add controls:
  * Version checks
  * Idempotency keys

== Improved Design: Safer Choices

* Changes problem solving to:
  * Proving workflow order
  * Rejecting invalid interleavings

== Failure Modes Overview

* Symptom: Single happy-path passes
  * Detection: Add repeated runs
  * Correction: Focus on invariant testing

* Symptom: Vague evidence
  * Detection: Lacks operation IDs
  * Correction: Capture structured evidence

* Symptom: Behavior changes not compared
  * Detection: No before/after scenario
  * Correction: Preserve failing test

== Trade-Off Analysis

[cols="1,1,1,1", options="header"]
|===
| Approach | Strengths | Weaknesses | When to Use
| Simple baseline | Easy to explain | Hides timing assumptions | First implementation
| Guarded transition | Protects invariant | Requires modeling | Status changes
| Explicit coordination | Visible dependencies | Can cause bottlenecks | Multi-object workflows
| Idempotent design | Handles duplicates | Requires deduplication | Asynchronous tasks
| Observability-first | Strong evidence | Adds instrument work | Failure proof assignments
|===
