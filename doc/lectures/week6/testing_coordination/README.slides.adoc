== Naive Implementation

* Assumption: Operation occurs once, in order
* Often invisible: sound method names, passing tests
* Basic flow: 
** Actor performs operation
** System reads state
** Applies transition
** Emits side effect

== Failure Scenario

* Overlapping execution yields stale state
* Executes twice or arrives late
* Mismatch between design assumption and execution model

== Corrected Design Direction

* Name the invariant and make transitions observable
* Add correctness controls: version checks, idempotency keys

== Improved Design Safety

* Proves invalid interleavings are rejected or contained
* Shifts focus from hoping to ensuring correctness

== Failure Modes

* Symptom: Passes single happy-path test
** Why: Avoids timing/order conditions
** Detect: Use repeated runs, concurrent actors
** Correct: Add failure-focused tests

* Symptom: Names tool, not design property
** Why: Focus on implementation not invariants
** Detect: Ask which invariant is protected
** Correct: Identify invariant first

* Symptom: Vague evidence
** Why: Logs lack essential information
** Detect: Evidence can't reconstruct failure
** Correct: Capture structured evidence

* Symptom: Changes behavior but unmeasured
** Why: Failure not repeatable
** Detect: No before/after run
** Correct: Keep failing test for comparison

== Trade-Off Analysis

* Approach: Simple baseline
** Strength: Easy to explain
** Weakness: Hides timing assumptions
** Use: First implementation

* Approach: Guarded state transition
** Strength: Protects invariant
** Weakness: Needs careful modeling
** Use: Status changes

* Approach: Explicit coordination
** Strength: Makes dependencies visible
** Weakness: Can cause deadlocks
** Use: Multi-object workflows

* Approach: Idempotent design
** Strength: Handles duplicates
** Weakness: Requires special handling
** Use: Queues and retries

* Approach: Observability-first design
** Strength: Strong evidence
** Weakness: Adds instrumentation
** Use: Design defense
