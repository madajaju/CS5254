== The Lost Signal

* **Definition**: Signal sent before the receiver waits.
* **Important**: Must be explicit to trust under pressure.
* **Mechanism**: Affects object state, timing, worker behavior.
* **Failure Mode**: Leads to duplicate work, stale state, blocked progress.
* **Design Implication**: Log transitions, validate via repeatable tests.

== Race to Wait

* **Definition**: Thread checks condition, finds it unmet, then meets condition before waiting.
* **Important**: Must be clearly defined for trust.
* **Mechanism**: Influences object state or worker behavior.
* **Failure Mode**: Results in duplicate work or blocked progress.
* **Design Implication**: Emphasize invariants and critical transitions.

== State-Based Signaling

* **Definition**: Signals based on current object state.
* **Important**: Necessary for trust in system behavior.
* **Mechanism**: Key to workflow timing and coordination.
* **Failure Mode**: Can produce misleading evidence.
* **Design Implication**: Maintain clear state checks and logging.

== Coordination Boundary

* **Definition**: Points where objects agree on progress.
* **Important**: Essential to ensure trustworthiness.
* **Mechanism**: Influences state and coordination.
* **Failure Mode**: Can lead to miscommunication; lost messages.
* **Design Implication**: Clearly define ownership and ordering.

== Progress Guarantee

* **Definition**: Ensures work completes rather than stalling.
* **Important**: Guarantees confidence in system behavior.
* **Mechanism**: Tied to object state and workflow timing.
* **Failure Mode**: Risks blockages and incomplete workflows.
* **Design Implication**: Validate transitions meticulously.

== Worked Example: Podcast Domain

* **Scenario**: `Ingestor` signals "File Ready." `Cleaner` isn't ready yet.
* **Fix**: `Cleaner` checks `episode.isIngested()` before waiting.

== Naive Implementation

* Assumes operation runs once in order.
* **Flow**:
  actor performs operation
  system reads current state
  system applies transition
  system emits side effect

== Failure Scenario

* Overlapping execution, delays, or partial failures lead to stale state or workflow blockages.
* The issue lies in mismatched design assumptions versus execution reality.

== Improvements Direction

* Name the invariant, make transitions observable.
* Implement correctness controls: version checks, retries, state-machine guards.

== Safer Design Justification

* Focus shifts from hope of execution order to proof against invalid interleavings.

== Failure Modes Overview

* **Symptom**: System passes happy-path, but fails under pressure.
  * **Detection**: Use structured logs, stress testing.
  * **Correction**: Add failure-focused tests targeting invariants.

== Trade-Off Analysis

[cols="1,1,1,1", options="header"]
|===
| Approach | Strengths | Weaknesses | When to Use
| Simple baseline | Easy to implement | Hides assumptions | First implementation
| Guarded transitions | Protects invariants | Needs careful modeling | Status updates
| Explicit coordination | Visibility of dependencies | May cause deadlocks | Multi-object workflows
|===
