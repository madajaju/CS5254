== Concept: Livelock

* Definition: Continuous state change without progress
* Importance: Must be made explicit for trust
* Mechanism: Object state, worker behavior, retries
* Failure mode: Duplicate work, stale state
* Design implication: Expose invariant, log transitions

== Naive Implementation

* Assumes operation happens once, in order
* Invisible assumption: sequential tests pass, but fail under pressure

== Naive Implementation Details

[.column]
* actor performs operation
* system reads current state

[.column]
* system applies transition
* system emits side effect

== Failure Scenario

* Overlapping execution can lead to stale state
* Failure isn't a syntax bug; it's a design assumption mismatch

== Improved Design Direction

* Name invariant, make transitions observable
* Use version checks, idempotency keys, explicit coordination

== Why the Improved Design is Safer

* Proves that invalid interleavings are rejected or contained
* Changes thinking from hope to validation

== Failure Modes and Anti-Patterns

* Symptom: Single happy-path demonstration passes
  * Cause: Tests avoid timing or pressure conditions
  * Detection: Add concurrent tests and structured logs
  * Correction: Add failure-focused tests

* Symptom: Naming tools instead of design properties
  * Cause: Focus on frameworks first
  * Detection: Identify which invariant is protected
  * Correction: State invariant before selecting mechanism

* Symptom: Vague evidence to support claims
  * Cause: Lack of operational context in logs
  * Detection: Reviewers can't reconstruct failure
  * Correction: Capture structured evidence linked to claims

* Symptom: Fix changes behavior without baseline comparison
  * Cause: Missed repeatable failure scenario
  * Detection: No before/after workload runs
  * Correction: Retain failing tests for reruns

== Trade-Off Analysis

* Approach: Simple baseline
  * Strengths: Easy to implement
  * Weaknesses: Hides timing assumptions
  * When to Use: First implementation

* Approach: Guarded transition
  * Strengths: Protects invariants
  * Weaknesses: Requires careful modeling
  * When to Use: Status changes

* Approach: Explicit coordination
  * Strengths: Makes dependencies clear
  * Weaknesses: Can introduce bottlenecks
  * When to Use: Multi-object workflows

* Approach: Idempotent design
  * Strengths: Handles duplicates
  * Weaknesses: Requires keys
  * When to Use: Queues and retries

* Approach: Observability-first
  * Strengths: Produces strong evidence
  * Weaknesses: Adds instrumentation
  * When to Use: Assignments needing proof
