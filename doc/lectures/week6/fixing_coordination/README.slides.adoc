== Explicit Wait States

* Importance: Ensures system trust under pressure
* Mechanisms: State, workflow timing, retries
* Failure mode: Duplicate work, stale state
* Design implication: Expose invariant, log transitions

== Naive Implementation

* Assumes single, ordered operation
* Often invisible in code
* Method name sounds correct

```text
actor performs operation
system reads current state
system applies transition
system emits side effect
```

== Failure Scenario

* Overlapping execution, delayed delivery
* Observes stale state, executes twice 
* Workflow left stuck
* Mismatch: design vs execution model

== Improved Design Direction

* Name the invariant
* Make transition observable
* Add correctness control
* Employ: version checks, idempotency keys

== Safer Design Justification

* Focus shifts from hoping for correct order
* Proves invalid interleavings handled

== Failure Modes & Anti-Patterns

* Symptoms: Single happy-path demonstration
  * Detection: Repeated runs, stress testing
  * Correction: Add failure-focused tests

* Symptoms: Naming tools over design properties
  * Detection: Ask about invariant protection
  * Correction: State invariant first

* Symptoms: Vague evidence
  * Detection: Reviewer cannot reconstruct
  * Correction: Capture structured evidence

* Symptoms: Behavior comparison missing
  * Detection: No before/after runs
  * Correction: Preserve failing test scenario

== Trade-Off Analysis

[cols="1,1,1,1", options="header"]
|===
| Approach | Strengths | Weaknesses | When to Use
| Simple baseline | Easy explanation | Hides timing assumptions | First implementation
| Guarded state | Protects invariant | Needs careful modeling | State changes
| Explicit coordination | Makes dependencies visible | Risk of deadlock | Multi-object workflows
| Idempotent design | Handles duplicates | Needs controls | Queues, retries
| Observability | Provides strong evidence | Needs instrumentation | Assignments needing proof
|===
