== Introduction

* A2 was not mainly about threads.
* It was about moving from shared-variable thinking to coordination thinking.
* The strongest submissions treated the system as a workflow of objects with clear responsibilities.
* The class patterns showed real progress from A1.

== Lesson 1: Stop Thinking About Threads

* The best projects rarely centered their explanation on threads.
* They focused on workflows, ownership, orchestration, events, and invariants.
* Weak submissions talked about locks first.
* Strong submissions talked about coordination first.

== Lesson 2: Ownership Beats Synchronization

* The best systems divided responsibility cleanly.
* Queue, coordinator, FSM, and domain object each had a different job.
* Correctness lived in ownership boundaries, not in any single lock.
* Good design made illegal transitions hard to express.

== Lesson 3: Queues Are Not Magic

* Adding a queue changes delivery, not correctness.
* A queue does not guarantee order, legality, uniqueness, or freshness.
* Several projects learned that "delivery is not correctness."
* The architecture still has to enforce the rules.

== Lesson 4: Invariants Matter

* The strongest submissions started describing system rules as invariants.
* They moved from "step B happens after step A" to "step B cannot happen unless condition A is true."
* That shift matters because it describes the system, not just the code.
* Architects think in invariants.

== Lesson 5: Failure Became a Design Tool

* In A1, failure usually meant a crash.
* In A2, failure meant the architecture allowed something illegal.
* Good teams intentionally exposed duplicate completion, stale validation, deadlock, races, and premature publication.
* The point was to locate where correctness actually lived.

== Lesson 6: Most Bugs Were Ownership Bugs

* Very few failures were pure thread bugs.
* Most were object design failures.
* Examples included workers mutating state they did not own and coordinators skipping validation.
* These are coordination problems first and synchronization problems second.

== Lesson 7: Message Passing Does Not Remove Coordination

* Different languages used different primitives.
* Python, Go, Rust, Java, C++, and Node still converged on the same architecture shape.
* Producer -> Coordinator -> State Machine -> Domain Object
* The language changed; the design pressure did not.

== Lesson 8: Synchronization Is Local

* Locks solve local access problems.
* Workflow solves global business problems.
* A mutex can protect an account object.
* A mutex cannot enforce a payment, shipping, and inventory sequence by itself.

== Lesson 9: AI Helped More With Syntax Than Architecture

* Almost every project used AI in some form.
* AI was helpful for syntax, queue APIs, channels, and locking code.
* AI was weaker on ownership, invariants, architecture, and failure analysis.
* The strongest students questioned AI output instead of copying it.

== Lesson 10: The Best Submissions Read Like Architecture Docs

* The best writeups did not read like code comments.
* They read like a system document:
** Architecture
** Workflow
** Ownership
** Invariants
** Failure
** Repair
** Evidence
** Validation

== Cross-Class Pattern

* Different domains still converged on the same structure.
* Examples included enrollment, trading, content pipelines, aircraft processing, and media workflows.
* The recurring ideas were explicit ownership, coordinated workflows, state transitions, and separation of responsibilities.
* That convergence is the real signal from A2.

== What Still Needs Improvement

* Testing: logs are not enough; assertions and repeatable tests matter.
* Failure analysis: students need to explain why the architecture allowed the bug.
* AI critique: documenting AI use is not the same as evaluating it.
* Engineers need to validate tool output, not just acknowledge it.

== Biggest Takeaway

* Correct concurrent systems come from clear ownership.
* They do not come from adding more synchronization.
* If one rule stays with you from A2, this is the one.

== Looking Ahead to A3

* A2 coordinated objects in one process.
* A3 removes shared memory.
* Locks disappear, method calls disappear, and object references disappear.
* The architecture lessons from A2 still apply: ownership, invariants, coordination, workflow, state transitions, and failure containment.

== Final Reflection

* The strongest solutions across the class converged on the same architectural ideas.
* That happened across different languages and different problem domains.
* Convergence is a sign that the ideas are fundamental, not accidental.
* A2 was about discovering those ideas and making them explicit.
