== Asynchronous Object Systems

=== Collective Strengths and Weaknesses

* Review of four A3 submissions
* Focus on architecture, correctness, evidence, and AI-assisted engineering
* Goal: move from _making systems asynchronous_ to _proving they are correct_

[.notes]
--
Use this opening to frame the review as a collective learning exercise rather than a ranking exercise.
--

== Assignment Intent

A3 asked students to evolve their A2 coordinated systems into asynchronous or event-driven object systems.

Students were expected to:

[.columns]
[.column]
--
* preserve continuity from A2
* identify blocking interactions
* design asynchronous workflows
* implement comparable behavior in two stacks
--

[.column]
--
* demonstrate async-specific failures
* add correctness controls
* compare blocking and asynchronous behavior
* critically evaluate AI assistance
--

== The Big Picture

The class was highly successful at:

* building asynchronous systems
* introducing event-driven structures
* improving object boundaries
* adding observability
* working critically with AI

The class was less consistent at:

* proving semantic equivalence
* defining invariants
* measuring throughput and latency
* validating emergent failure behavior
* consolidating evidence

== Strength 1: Continuity from A2

All strong submissions treated A3 as an evolution rather than a restart.

Students generally:

* preserved the original domain
* retained core object responsibilities
* mapped A2 workflow stages into A3
* isolated what changed and why
* documented intentional redesigns

=== Why This Matters

Architectural evolution is more realistic than greenfield redesign.

Professionally, engineers rarely get to start over.

The strongest work demonstrated:

* respect for existing responsibilities
* controlled refactoring
* bounded architectural change
* clear migration reasoning

=== Why Correlation Matters

Without correlation:

[source,text]
----
Worker started
Retrying
Publish complete
Processing failed
----

With correlation:

[source,text]
----
correlationId=abc123 event=PROCESS_REQUESTED
correlationId=abc123 attempt=2 event=PUBLISH_RETRY
correlationId=abc123 state=PUBLISHED
----

== Weakness 1: Implementation Outpaced Correctness

The most common weakness was not implementation quality.

It was insufficient proof that the asynchronous system preserved the original behavior.

Many students explained correctness.

Fewer demonstrated it.

=== Missing Evidence

Few submissions included a deterministic test that:

. runs identical input through A2
. runs identical input through A3
. waits for asynchronous completion
. compares final object state
. compares side effects
. fails on any semantic difference

Asynchronous execution should change coordination.

== Weakness 2: Blocking Analysis Was Sometimes Superficial

Most students found blocking calls.

Not all explained the system-level consequences.

Weak analysis:

[source,text]
----
This method blocks.
----

Strong analysis:

[source,text]
----
The caller remains occupied until all downstream stages complete,
which increases response latency, couples lifecycle management,
limits independent scaling, and makes failures propagate synchronously.
----

== Weakness 3: Failure Injection Dominated

Many failures were demonstrated by:

* forced exceptions
* configuration flags
* artificial delays
* manually duplicated events

These are valid techniques, but they are not the whole story.

=== Missing Emergent Failures

Students should also explore failures that arise naturally from concurrency:

[.columns]
[.column]
--
* race conditions
* stale reads
* conflicting updates
* timing windows
--

[.column]
--
* reordered completion
* task completion after cancellation
* cross-worker ownership conflicts
--

== Weakness 4: Performance Claims Were Under-Measured

Most submissions claimed improved responsiveness.

Few measured it rigorously.

Useful metrics would include:

[.columns]
[.column]
--
* submission latency
* end-to-end latency
* workflows per second
* queue depth
--

[.column]
--
* average retry count
* worker utilization
* backlog growth
* time to recovery
--

=== Responsiveness Is Not Throughput

An async design may return control quickly while total processing time remains unchanged.

[source,text]
----
Submission latency  !=  End-to-end latency
Responsiveness      !=  Throughput
Concurrency         !=  Correctness
----

== Weakness 5: State Machines Were Underused

Many projects tracked status.

Fewer defined an explicit state machine.

=== Why State Machines Help

A state machine makes legal and illegal transitions visible.

[plantuml, workflow-state-machine, svg, width=100%]
----
@startuml
skinparam BackgroundColor transparent
skinparam shadowing false
skinparam DefaultFontColor #263238
skinparam ArrowColor #455a64
skinparam ArrowFontColor #37474f
skinparam state {
  BackgroundColor #f7f9fa
  BorderColor #455a64
  FontColor #263238
}
left to right direction

[*] --> RECEIVED
RECEIVED --> PROCESSING : begin
PROCESSING --> PROCESSED : work succeeds
PROCESSING --> PROCESSING_FAILED : work fails
PROCESSING_FAILED --> PROCESSING : retry allowed
PROCESSED --> PUBLISHING : publish requested
PUBLISHING --> PUBLISHED : publish succeeds
PUBLISHING --> PUBLISH_FAILED : publish fails
PUBLISH_FAILED --> PUBLISHING : retry allowed
PUBLISHED --> [*]

PROCESSING_FAILED -[#c0392b]-> [*] : retries exhausted
PUBLISH_FAILED -[#c0392b]-> [*] : retries exhausted
@enduml
----

=== What State Machines Clarify

They help answer:

[.columns]
[.column]
--
* Can this event run in the current state?
* Is this transition legal?
* Is this event stale?
--

[.column]
--
* Has this workflow already completed?
* Should this retry continue?
* Can this side effect occur twice?
--

== Collective Lesson 1

=== Asynchronous Does Not Mean Faster

Async design may improve:

[.columns]
[.column]
--
* responsiveness
* resource utilization
* stage independence
--

[.column]
--
* fault isolation
* scalability potential
--

It may also increase:

[.columns]
[.column]
--
* complexity
* latency variance
* debugging difficulty
--

[.column]
--
* failure modes
* correctness risk
--

== Collective Lesson 2

=== Duplicate Messages Are Normal

Reliable asynchronous systems should assume:

[.columns]
[.column]
--
* a message may arrive more than once
* a message may arrive late
* a retry may repeat a side effect
--

[.column]
--
* a worker may fail after completing work
* completion events may be delayed
--

Correctness controls should be designed around those assumptions.

== Collective Lesson 3

=== Observability Is Part of the Architecture

Logging is not an afterthought.

For async systems, observability must be designed into:

[.columns]
[.column]
--
* messages
* workers
* retries
--

[.column]
--
* state transitions
* side effects
* final completion
--

== Collective Lesson 4

=== AI Can Accelerate Design, Not Replace Judgment

Good AI-assisted engineering requires:

* domain understanding
* architectural skepticism
* verification
* evidence
* ownership of the final decision

== Recommendations for Future A3 Assignments

=== Require Deterministic Equivalence

Students should prove:

[source,text]
----
A2 semantics == A3 semantics
----

for a controlled workload.

=== Require Quantitative Evidence

At minimum, capture:

* submission latency
* end-to-end completion time
* throughput under concurrency
* queue depth during load

=== Require Explicit Invariants

Examples:

* an item cannot publish before processing
* the same side effect occurs at most once
* final state is terminal
* stale events cannot overwrite newer state
* retries terminate

=== Require a State Machine

Each submission should document:

* states
* legal transitions
* invalid transitions
* terminal states
* retry behavior

=== Standardize the Integrity Packet

Use one consistent structure across all students.

This will improve:

* grading consistency
* student reflection
* AI accountability
* evidence quality

== Proposed A3 Maturity Model

[cols="1,2",options="header"]
|===
|Level |Characteristics

|1 — Async Syntax
|Uses threads, promises, or async/await

|2 — Async Workflow
|Introduces queues, events, and workers

|3 — Observable Async System
|Adds correlation, status, and structured logs

|4 — Correct Async System
|Adds invariants, idempotency, sequencing, and guards

|5 — Validated Async Architecture
|Proves equivalence, measures behavior, and documents limitations
|===
